## 1. 없는 화면

### 1.1 대시보드

| | |
| --- | --- |
| **현재** | 의도된 IA의 ① 대시보드(전원 공통)가 없다. 각자 자기 업무 화면에 직접 들어가 확인해야 하며, **"지금 내가 무엇을 해야 하는가"를 알려주는 화면이 시스템 전체에 없다.** |
| **결정할 것** | 도입할지, 도입한다면 역할별 위젯을 어디까지 둘지 |
| **결정 주체** | 서비스운영팀 + 운영지원팀 |
| **바뀌는 것** | 사이드바 최상단 메뉴, 로그인 후 랜딩 규칙 |

설계 문서가 정의한 위젯: 이번 주차 출석 미제출 팀(운영지원팀·HOST) / 내 평가 진행률(평가자) / 모집 진행 상태·D-Day(서비스운영팀).

### 1.2 설정과 내부 공지사항

| | |
| --- | --- |
| **현재** | ⑦ 설정 L1이 없다. 내부 공지사항은 설계 문서가 스스로 "백엔드가 없다. P2로 두거나 IA에서 제거할지 결정 필요"로 남겨둔 항목이며 아직 미결이다. |
| **결정할 것** | 설정 메뉴를 만들지, 공지사항을 도입할지 아니면 IA에서 뺄지 |
| **결정 주체** | 서비스운영팀 |
| **바뀌는 것** | 사이드바 최하단 메뉴 유무 |

### 1.3 출결 대시보드의 위치

> **결정 완료.** 정본은 [`spec/05-attendance.md`](../spec/05-attendance.md) §2.

| | |
| --- | --- |
| **결정 — 대시보드** | **두지 않는다.** v2.0 IA에 출결 대시보드 화면이 없다. 종합 조회는 `ATT-VIEW`(read-only), 집계는 `ATT-SUM`이 담당한다 |
| **결정 — 리더 입력** | `ATT-LDR`을 **정식 화면으로 IA에 올린다.** 역할 전환으로만 도달하는 구조를 없앤다. HOST의 랜딩은 담당 그룹 목록(`LDR-01`)이며, 사이드바 노출은 permission 기반 게이팅(`SYS-GATE`)이 정한다 |
| **바뀐 것** | PoC의 역할 전환 토글·퀵 로그인은 제거 대상이 된다 (§3.1과 함께 처리) |

## 2. 도메인을 가로지르는 사항

### 2.1 결과 처리 3단계

| | |
| --- | --- |
| **현재** | 설계는 `CSV 추출 → 합격자 승격 → 지원서 전체 삭제`를 **한 화면에 순서대로** 두어 실행 순서를 강제하도록 했고, 설계 원칙에 "순서가 어긋나면 복구 불가"로 명시되어 있다. 현재는 CSV 추출이 리크루팅 영역으로 분리됐고, 승격만 서류 평가에 남았으며, **지원서 전체 삭제는 구현되어 있지 않다.** |
| **결정됨 — 배치** | **분리된 구조를 유지한다.** CSV 추출은 리크루팅에 `REC-CSV`로 남기고, 승격은 `EVL-PROM`, 지원서 전체 삭제는 `EVL-DEL` 신규 화면으로 둔다. 정본은 [`spec/04-evaluation.md`](../spec/04-evaluation.md) §4.4 |
| **결정됨 — 순서 강제** | 한 화면으로 묶는 대신 **조건 게이팅으로 대체한다.** `DEL-01`이 모집 비활성 · 승격 완료 두 조건과 CSV 추출 완료 여부를 표시하고, 미충족 시 실행 버튼을 비활성화하며 사유를 노출한다. 모집 진행 중이면 서버가 차단한다 |
| **남은 결정** | 진입 자체를 막을지(승격 미완료 시 화면 진입 차단) 여부. `EVL-B-6`으로 이관되어 디자인 단계에서 정한다 |
| **결정 주체** | 대표진 + 서비스운영팀 (배치·강제 방식 확정 완료) |

**왜 이렇게 정리됐는가.** 세 액션을 한 화면에 묶은 것은 UI 취향이 아니라 **순서를 강제하는 장치**였다. 이미 CSV가 리크루팅으로 떨어져 나간 상태에서 삭제를 단독 화면에 만들면 순서 강제가 사라진 채로 굳는다는 것이 이 안건의 핵심 우려였다. 기능명세서는 화면을 다시 묶는 대신 **삭제 화면 자체에 선행 조건 검사를 넣어** 같은 효과를 내는 방식을 택했다. "승격 안 한 상태로 삭제 → 복구 불가"는 `DEL-01`의 조건 표시와 서버 차단으로 막힌다.

**부수 사항:** 지원서에는 대학교·전공·생년월일·연락처·병역이 포함된다. 설계는 시즌 종료 시 일괄 삭제를 전제했으나 삭제 수단이 없어 기수가 쌓일수록 보관 데이터가 누적된다.

### 2.2 사전 알림 명단의 기능 범위

> **결정 완료.** 정본은 [`spec/03-recruiting.md`](../spec/03-recruiting.md) §4.5다. 이 절은 다른 문서가 가리키는 링크를 살리기 위해 결론만 남긴다.

| | |
| --- | --- |
| **결정** | 초과 기능을 **정리한다.** 사전 알림에는 `PRE_NOTIFICATION_READ`·`PRE_NOTIFICATION_DELETE` 두 permission만 존재하므로, 신청자 직접 등록 · 발송 상태 토글 · `발송 상태` 컬럼 · 맞춤 알림 열을 제거한다. 명단은 공개 신청 폼(`POST /api/v1/recruitment/subscriptions`)으로만 수집한다 |
| **발송 방식** | 카카오/SMS 연동을 하지 않는다. 담당자가 문구를 복사해 외부 메신저로 직접 발송하며, 시스템은 발송 상태를 기록하지 않는다. 발송 이력이 필요하면 시스템 밖에서 관리한다 |
| **개별 삭제** | 유지한다. `PRE_NOTIFICATION_DELETE`가 개별·전체 삭제를 모두 덮으며, 삭제는 T0.7 확인 모달을 거친다 |
| **메시지 양식** | localStorage에서 **서버 저장으로 이전**한다 (`ALM-03`) |
| **남은 작업** | [`01-wbs.md`](../01-wbs.md) `REC-ALM` 티켓. `REC-API-3`(발송 상태 갱신 경로)은 이 결정으로 해소됨 |

### 2.3 ADV 입력 화면

> **결정 완료.** 정본은 [`spec/05-attendance.md`](../spec/05-attendance.md) §4.4 · §4.7.

| | |
| --- | --- |
| **결정 — 축 전환** | 화면을 **활동별이 아니라 주체별로 가른다.** 운영지원팀 컨펌 화면은 `ATT-ADV`(주차 그리드)와 `ATT-STD`(회차 그리드)로 나누고, 리더 입력은 활동 구분 없이 `ATT-LDR` 하나로 둔다 |
| **왜 갈라지나** | ADV는 **주차 단위**이고 상태값이 4종(출석·결석·비대면·미기록)인 반면, 스터디는 **회차 단위**이고 3종(출석·결석·미기록)이다. 비대면 규칙도 ADV에만 있다. 운영지원팀이 보는 그리드는 축과 상태값이 달라 합칠 수 없다 |
| **왜 리더는 하나인가** | 리더의 작업은 둘 다 "담당 그룹 → 주차/회차 선택 → 상태 입력 → 인증 사진 제출"로 같다. 겸임자는 `LDR-01` 목록에 ADV·스터디가 함께 뜬다 |

### 2.4 HOST 계정 관리의 위치

> **결정 완료.** 정본은 [`spec/05-attendance.md`](../spec/05-attendance.md) §4.10.

| | |
| --- | --- |
| **결정** | **출결 영역에 유지한다.** 다만 독립 화면(`SET-HOST`)으로 두지 않고 스터디·팀 관리(`ATT-GROUP`)에 **흡수한다** |
| **왜** | 계정 발급은 그 자체가 목적이 아니라 **장 지정의 부수 결과**다. 팀 생성 → 장 지정 → 계정 발급이 한 동선이라 화면을 가르면 왕복이 생긴다 (`GRP-02`~`GRP-05`) |
| **재발급 처리** | 기존 계정이 있으면 ID/PW를 다시 내지 않고 **리더십만 추가**한다. 스터디를 여러 개 맡으면 리더십 행이 여러 개다 |
| **회수** | 기수말 soft delete + 토큰 정리 (`GRP-06`) |

### 2.5 활동·주차·팀 편성

> **결정 완료.** 정본은 [`spec/05-attendance.md`](../spec/05-attendance.md) §3.4 · §4.1 · §4.10 · §4.11.

| | |
| --- | --- |
| **결정 — 편성 화면** | **신설한다.** 명단은 `ATT-ROSTER`(SOT), 그룹은 `ATT-GROUP`, 주차 일정은 `SET-RULE`이 맡는다 |
| **결정 — 회차 생성 주체** | **운영지원팀.** 주차·회차 구조는 `SET-RULE`의 Term 설정에서 미리 만들어지고, 리더는 만들어진 주차/회차를 **선택만** 한다. HOST가 세션을 생성하던 동선을 없앤다 |
| **결정 — 대상자 산정** | `ATT-ROSTER`가 SOT이고 각 출결 화면의 명단은 **조회 시점 계산**이다. 스냅샷을 복사하지 않으므로 명단 수정이 즉시 전 화면에 반영된다. 행사는 `(필참 ∪ 참여) ∩ 선택 기수·부문` |
| **BASE 병행 인원** | **자동 포함**으로 확정. 참여 상태 개념 없이 해당 부문 병행 지정자를 포함하고 행에 "병행" 표시를 붙이며, 감점은 동일하다 (`BASE-03`) |

### 2.6 인증 방식과 확인 절차

> **결정 완료.** 정본은 [`spec/05-attendance.md`](../spec/05-attendance.md) §6.1 · §9 ATT-A-4.

| | |
| --- | --- |
| **결정 — 인증 방식** | **인증 사진 제출로 확정한다.** 2026-09-10 기획안이 카페 링크로 정했던 것을 뒤집는 결정이며, 현재 구현의 사진 업로드가 정본에 부합하게 됐다 |

| **남은 것** | 사진 저장 위치·용량 제한은 `ATT-CORE` 스키마 작업에서 정한다 |
| **함께 처리** | [`91-ia-gap.md`](91-ia-gap.md) §3 출결 인증 방식 행과 §4 #4를 사진 확정으로 갱신했다 |

### 2.7 점수 규칙과 점수 집계의 연결

> **방향 확정, 구현 범위는 백엔드 검토 중.** 정본은 [`spec/05-attendance.md`](../spec/05-attendance.md) §4.11.

| | |
| --- | --- |
| **결정 — 반영 범위** | 규칙 변경은 **그 Term 안에서만 반영되고 지난 Term 집계에는 소급하지 않는다.** 점수값을 **Term 단위로 보관**하는 이유가 이것이다. 회칙이 개정돼도 지난 Term 집계가 보존되어야 한다 |
| **결정 — 오버라이드** | **행사 단위 오버라이드**를 둔다. 예: OT(멘토) 시트의 결석 점수를 −5로 (멘토 특칙) |
| **결정 — 규칙 화면** | 문서용이 아니라 **실제 계산에 연결되는 화면**이다. `ATT-TL`의 `TL-04`가 각 점수에 적용된 Term 규칙을 함께 표시한다 |
| **남은 것** | Term 보관 구조와 행사 오버라이드 계층의 구현 범위 — `ATT-B-1`, 백엔드 검토 중 |
| **우선 조치** | 기존 안내 문구("전체 출결 표와 시트 수식에 반영되었습니다")는 소급 반영을 암시하므로 정정 대상이다 |

### 2.8 지원자 데이터의 단일 기준

| | |
| --- | --- |
| **현재** | 리크루팅 영역과 서류 평가 영역이 각각 별도의 지원자 데이터를 기준으로 구성되어 있어, 공고·문항 수정이 평가 화면에 반영되지 않는다. 사전 알림 명단과 실제 지원자를 잇는 식별 키도 없다. |
| **결정할 것** | 백엔드 지원자 API를 단일 기준으로 삼는 연동 구조. 사전 알림 신청자의 지원 전환을 추적할지 |
| **결정 주체** | 백엔드 + 서비스운영팀 |
| **바뀌는 것** | 두 영역의 데이터 흐름. 추적한다면 식별 키(이메일·연락처)와 개인정보 처리 근거가 필요 |

## 3. 전역 사항

### 3.1 역할 기반 접근 제어

> **결정 완료.** 정본은 [`spec/06-system.md`](../spec/06-system.md) §3.

| | |
| --- | --- |
| **결정 — 역할 모델** | `MASTER` · `SUPER` · `TEAM` · `HOST` 4종에 `TeamName` 축을 곱한 **기본 세트 키 7개** 체계로 확정. `TeamName`은 팀명이 아니라 운영진의 자리이며 `그룹리더`가 추가된다. `CONTENT_ADMIN`은 41개 카탈로그에 대응 키가 없어 폐기된다 |
| **결정 — 권한 단위** | Permission **41개**를 직접 쓴다. `spec/02-role-model.md` §2의 10종 묶음 이름은 폐기된다 |
| **결정 — 판정 근거** | 프론트는 매트릭스를 하드코딩하지 않고 `GET /admin/accounts/me`가 내려주는 **유효 permission 목록**으로만 판정한다 |
| **결정 — 메뉴 처리** | **숨긴다.** 권한 없는 메뉴는 미노출이고, 경로 직접 진입은 가드 + 403 화면으로 막는다. 실제 차단은 백엔드 `@PreAuthorize` 2층이 한다 |
| **결정 — 라우터** | 도입한다. 경로 가드가 성립해야 2중 구조가 완성된다 (`T0.1a`) |
| **함께 처리 (유지)** | 최종 평가 버튼을 `FINAL_DECISION_WRITE` 보유자로 제한 · HOST의 관리자 API 경로 차단 · PoC용 역할 전환 장치 제거 |
| **남은 것** | 구현은 [`spec/06-system.md`](../spec/06-system.md) §7의 권한 재설계 0~5단계. `spec/02-role-model.md` §3의 `UserRole`/`AdminRole` 타입 일원화는 프론트 작업으로 남는다 |

### 3.2 출결 상태 값 체계

> **결정 완료.** 정본은 [`spec/05-attendance.md`](../spec/05-attendance.md) §3.2.

| | |
| --- | --- |
| **결정 — 값 체계** | **9종 단일 enum으로 통일한다.** 출석 · 지각 · 조퇴 · 사유결석 · 인정결석 · 비대면 · 무단지각 · 무단결석 · 미기록 |
| **결정 — 점수 방향** | **감점 체계**다. 출석·인정결석·비대면·미기록이 0이고 나머지가 음수다. 가점 체계(출석 +1)는 폐기한다 |
| **결정 — CSV 코드** | `1 / 2 / 3 / 4 / 5 / 6`과 무단 계열 `O` · `X`, **미기록은 빈 칸**. 기존 운영지원팀 집계 시트 체계를 그대로 따른다. `-`나 `—` 같은 기호는 엑셀에서 텍스트로 잡혀 계산식에 걸리므로 쓰지 않는다 |
| **결정 — 활동별 부분집합** | 단일 enum을 활동별로 부분집합으로 쓴다. ADV는 4종(결석은 사유결석 −3, 무단 구분 없음), 스터디는 3종(사유결석 불허, 지각은 출석 처리) |
| **화면 ↔ CSV** | 화면에는 상태명을 쓰고 CSV 추출 시에만 코드로 변환한다 |

### 3.3 되돌릴 수 없는 작업의 확인 절차

| | |
| --- | --- |
| **현재** | 설계는 파괴적 액션에 2단 확인 모달과 대상 표시를 요구하지만, 대부분 단일 확인창이거나 확인이 아예 없다. |
| **결정할 것** | 어떤 작업에 어느 수준의 확인을 둘지. 승격 취소는 "두지 않음"으로 확정됐고(아래), 나머지 도메인 작업은 미결 |
| **결정 주체** | 대표진 + 백엔드 |
| **바뀌는 것** | 아래 작업들의 실행 동선 |

확인 절차가 **전혀 없는** 작업 — 우선 처리 대상:

| 작업 | 화면 | 영향 |
| --- | --- | --- |
| 최종 합불 확정 | [03](03-evaluation.md) | 드롭다운 한 번으로 확정. 이력 없음. 승격 대상을 결정함. **확정 시 `HOLD`·`PENDING` 0건 검증을 거치도록 결정됨** (→ [`spec/04-evaluation.md`](../spec/04-evaluation.md) §4.1) |
| 선택 인원 일괄 발송 완료 | [02](02-recruiting.md) | 되돌리려면 건별 수동 복구 |
| 부원 불러오기 | [04](04-attendance.md) | 클릭 즉시 명단 추가 |

확인이 **한 번뿐인** 작업: 아카이빙 삭제(S3 이미지 동반) · 공고 삭제(참조 검사 없음) · 행사 삭제(출석 명단 동반) · 명단 CSV 업로드(전체 교체).

**취소 경로가 없는** 작업: 정회원 승격 — **결정됨.** 화면에 취소 기능을 두지 않고 실행 전 확인 모달(대상 인원 수 · 명단 · "되돌릴 수 없습니다" 문구)로 대체한다. 오승격이 실제로 발생하면 백엔드에서 직접 처리하며, 실행 기록은 감사 로그(§3.4) 대상이다. → [`spec/04-evaluation.md`](../spec/04-evaluation.md) §4.3

**필터가 적용된 상태에서 전체 선택 시 화면에 보이지 않는 대상까지 선택되는** 문제도 함께 처리한다(사전 알림 명단).

### 3.4 감사 로그의 기록 범위

> **구현 확정, 세부 스펙은 착수 시 확정.** 정본은 [`spec/06-system.md`](../spec/06-system.md) §4.3.

| | |
| --- | --- |
| **결정 — 구현 여부** | **구현한다.** 다만 권한 재설계(v3) 범위 밖이라 **별도 착수**한다. 감사 로그 구현체가 현재 코드에 없고, 권한 구현이 끝난 뒤 붙인다 |
| **결정 — 기록 대상(기본안)** | 되돌릴 수 없는 작업 — 출결 수정 · 콘텐츠 삭제 · 합불 확정 · 승격 · 계정 생성 · 권한 변경 · 지원서 삭제 |
| **남은 것** | 저장 항목 · 조회 조건 · 보관 기간은 착수 시 백엔드와 확정한다 — `SYS-A-2` |
| **그동안의 공백** | 감사 로그가 붙기 전까지 권한 변경 이력은 DB 오버라이드 행(`granted_by` · `created_at`)으로만 남는다 |

관련: 예외 승인 거절 시 사유 기록 없음. 운영지원팀 수정 시 리더가 작성한 원본 사유가 덮어써짐.
