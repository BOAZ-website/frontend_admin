## 1. 없는 화면

### 1.1 대시보드

| | |
| --- | --- |
| **현재** | 의도된 IA의 ① 대시보드(전원 공통)가 없다. 각자 자기 업무 화면에 직접 들어가 확인해야 하며, **"지금 내가 무엇을 해야 하는가"를 알려주는 화면이 시스템 전체에 없다.** |
| **결정할 것** | 도입할지, 도입한다면 역할별 위젯을 어디까지 둘지 |
| **결정 주체** | 서비스운영팀 + 운영지원팀 |
| **바뀌는 것** | 사이드바 최상단 메뉴, 로그인 후 랜딩 규칙 |

설계 문서가 정의한 위젯: 이번 주차 출석 미제출 팀(운영지원팀·HOST) / 내 평가 진행률(평가자) / 모집 진행 상태·D-Day(서비스운영팀).

### 1.2 설정과 내부 공지사항

| | |
| --- | --- |
| **현재** | ⑦ 설정 L1이 없다. 내부 공지사항은 설계 문서가 스스로 "백엔드가 없다. P2로 두거나 IA에서 제거할지 결정 필요"로 남겨둔 항목이며 아직 미결이다. |
| **결정할 것** | 설정 메뉴를 만들지, 공지사항을 도입할지 아니면 IA에서 뺄지 |
| **결정 주체** | 서비스운영팀 |
| **바뀌는 것** | 사이드바 최하단 메뉴 유무 |

### 1.3 출결 대시보드의 위치

| | |
| --- | --- |
| **현재** | 출결 대시보드와 리더 출결 입력 화면이 **사이드바에 없다.** 특정 역할로 로그인하거나 역할을 전환할 때만 도달한다. |
| **결정할 것** | 정식 메뉴로 노출할지, 역할별 시작 화면으로만 둘지 |
| **결정 주체** | 운영지원팀 |
| **바뀌는 것** | 사이드바 구조. 역할 제어 적용 시 두 화면의 노출 규칙 |

## 2. 도메인을 가로지르는 사항

### 2.1 결과 처리 3단계

| | |
| --- | --- |
| **현재** | 설계는 `CSV 추출 → 합격자 승격 → 지원서 전체 삭제`를 **한 화면에 순서대로** 두어 실행 순서를 강제하도록 했고, 설계 원칙에 "순서가 어긋나면 복구 불가"로 명시되어 있다. 현재는 CSV 추출이 리크루팅 영역으로 분리됐고, 승격만 서류 평가에 남았으며, **지원서 전체 삭제는 구현되어 있지 않다.** |
| **결정할 것** | 세 단계를 한 화면으로 복원할지, 분리된 구조를 유지할지 |
| **결정 주체** | 대표진 + 서비스운영팀 |
| **바뀌는 것** | 리크루팅 CSV 화면의 존폐, 승격 화면의 범위, 지원서 삭제 기능의 배치 |

**왜 지금 결정해야 하는가.** 지금은 삭제 기능이 없어 "승격 전에 실수로 삭제"가 일어날 수 없다. 그러나 세 액션을 묶은 것은 UI 취향이 아니라 **순서를 강제하는 장치**였고, 이미 CSV가 떨어져 나간 상태에서 삭제를 나중에 또 다른 화면에 단독으로 만들면 순서 강제가 완전히 사라진 채로 굳는다. 그때는 "승격 안 한 상태로 삭제 → 복구 불가"가 실제로 가능해진다.

**부수 사항:** 지원서에는 대학교·전공·생년월일·연락처·병역이 포함된다. 설계는 시즌 종료 시 일괄 삭제를 전제했으나 삭제 수단이 없어 기수가 쌓일수록 보관 데이터가 누적된다.

### 2.2 사전 알림 명단의 기능 범위

| | |
| --- | --- |
| **현재** | 설계는 "목록 추출 → 대표진 전달 → 전체 삭제"로 정의하고 **개별 삭제 API가 없다**고 명시한다. 구현에는 개별 등록·개별 삭제·발송 상태 토글·문구 템플릿 편집기가 있다. |
| **결정할 것** | 초과 기능을 정리할지, 유지하고 백엔드에 신규 API를 요청할지. 발송을 수동 복사로 둘지 카카오/SMS를 연동할지 |
| **결정 주체** | 서비스운영팀 + 백엔드 |
| **바뀌는 것** | 사전 알림 화면 전체 구성. 유지 시 백엔드 작업 추가 |

### 2.3 ADV 입력 화면

| | |
| --- | --- |
| **현재** | 사이드바의 "ADV 입력 및 증빙"과 "스터디 입력 및 증빙"이 **같은 화면을 연다.** ADV 전용 입력 화면은 없다. |
| **결정할 것** | ADV 전용 화면이 필요한지, 하나로 합칠지 |
| **결정 주체** | 운영지원팀 |
| **바뀌는 것** | 사이드바 메뉴 수, 리더 입력 화면의 대상 구분 방식 |

이건 "구현이 덜 됐다"가 아니라 **ADV 팀장의 입력 작업이 스터디장과 다른가**라는 업무 질문이다.

### 2.4 HOST 계정 관리의 위치

| | |
| --- | --- |
| **현재** | 설계는 HOST 계정 관리를 ⑥ 회원·권한 관리에 두고 평가자 계정 일괄 생성 흐름을 재사용하도록 했다. 구현은 출결 하위(설정)에 있다. |
| **결정할 것** | 계정 관리 영역으로 옮길지, 출결 영역에 유지할지 |
| **결정 주체** | 서비스운영팀 + 운영지원팀 |
| **바뀌는 것** | 두 허브의 메뉴 구성. 계정 발급 흐름의 공통화 여부 |

발급·회수 주체가 운영지원팀이라는 점([`spec/01`](../spec/01-attendance-system.md) §2-4)은 확정되어 있어, 업무 동선상 출결 영역에 두는 편이 자연스러울 수 있다.

### 2.5 활동·주차·팀 편성

| | |
| --- | --- |
| **현재** | 설계의 2.5(활동 등록 · 주차 일정 등록 · 팀 생성·팀원 배정)가 미착수다. 명단이 고정 데이터이고, 회차를 만드는 진입점도 없다. 설계 스펙의 HOST 매주 동선("주차 선택 → 세션 생성 → 제출")의 시작점이 막혀 있다. |
| **결정할 것** | 회차 생성 주체가 HOST인지 운영지원팀인지. 출결 대상자를 어떤 기준으로 뽑을지(기수·부문 필터) |
| **결정 주체** | 운영지원팀 |
| **바뀌는 것** | 편성 화면 신설 여부, 리더 입력 화면의 진입 동선, 명단 관리 방식 |

「BASE 병행 인원 자동 포함」도 같은 뿌리의 문제다.

### 2.6 인증 방식과 확인 절차

| | |
| --- | --- |
| **현재** | 설계 문서 전반은 **네이버카페 인증 링크**를 전제하지만 구현은 **출석 인증 사진 업로드**다. 사진 확인은 "확인 완료 처리"만 있고 **반려 경로가 없으며**, 확인 여부가 대시보드 매트릭스에 표시되지 않아 검토 완료와 미검토를 구분할 수 없다. |
| **결정할 것** | 사진 인증을 정본으로 확정할지. 확인 / 반려 / 재제출 절차를 어떻게 설계할지. 사진 저장 위치·용량 제한 |
| **결정 주체** | 운영지원팀 |
| **바뀌는 것** | 출결 확정 절차 전체. 대시보드 매트릭스의 상태 표시. IA 문서 §6 #4 삭제 |

설계 문서 §6 #4가 "실제 접근 확인은 네이버 로그인 이슈로 불가"라고 스스로 카페 방식의 한계를 적어둔 만큼, 사진 인증이 그 제약의 귀결로 보인다. 확정되면 IA 문서를 갱신한다.

### 2.7 점수 규칙과 점수 집계의 연결

| | |
| --- | --- |
| **현재** | 점수 규칙 화면은 저장 시 "전체 출결 표와 시트 수식에 반영되었습니다"로 안내하지만, 출결 점수 집계 화면은 고정 배점을 쓴다. 규칙을 참조하는 화면은 BASE·ADV·스터디 출결 관리뿐이다. |
| **결정할 것** | 규칙 변경이 집계에 반영되어야 하는지 |
| **결정 주체** | 운영지원팀 + 대표진 |
| **바뀌는 것** | 점수 규칙 화면의 존재 의미. 연결하지 않을 경우 안내 문구를 고치고 규칙 화면을 문서용으로 재정의해야 함 |

**잘못된 점수로 수료 판정이 나갈 수 있으므로 안내 문구만이라도 우선 정정한다.**

### 2.8 지원자 데이터의 단일 기준

| | |
| --- | --- |
| **현재** | 리크루팅 영역과 서류 평가 영역이 각각 별도의 지원자 데이터를 기준으로 구성되어 있어, 공고·문항 수정이 평가 화면에 반영되지 않는다. 사전 알림 명단과 실제 지원자를 잇는 식별 키도 없다. |
| **결정할 것** | 백엔드 지원자 API를 단일 기준으로 삼는 연동 구조. 사전 알림 신청자의 지원 전환을 추적할지 |
| **결정 주체** | 백엔드 + 서비스운영팀 |
| **바뀌는 것** | 두 영역의 데이터 흐름. 추적한다면 식별 키(이메일·연락처)와 개인정보 처리 근거가 필요 |

## 3. 전역 사항

### 3.1 역할 기반 접근 제어

| | |
| --- | --- |
| **현재** | 사이드바는 모든 계정에 24개 메뉴를 전부 노출한다. 역할 분기가 동작하는 곳은 시스템·계정 화면 하나뿐이다. 게다가 **역할 정의가 문서·코드에 걸쳐 네 갈래로 갈라져 있다.** 설계가 요구하는 "사이드바 미노출 + 경로 가드" 2중 구조 중 두 번째 층은 라우터가 없어 만들 수 없다. |
| **결정할 것** | ① 역할 모델 정본 (`CONTENT_ADMIN` 처리, 타입 일원화) ② 메뉴를 숨길지 보이되 차단할지 ③ 라우터 도입 여부 |
| **결정 주체** | 서비스운영팀 + 대표진 + 백엔드 |
| **바뀌는 것** | 전 도메인의 화면 진입 정책. **역할 정본이 정해지기 전에는 접근 제어를 구현할 수 없다.** |

상세는 [`spec/02-role-model.md`](../spec/02-role-model.md) §3. 함께 처리할 항목:
- 최종 평가 버튼을 대표진(SUPER) 전용으로 제한 (설계가 명시했으나 누락)
- HOST의 관리자 API 접근 차단 (경로 단위)
- PoC용 역할 전환 장치 제거 (로그인 시뮬레이션 · 계정 전환)

### 3.2 출결 상태 값 체계

| | |
| --- | --- |
| **현재** | 세 벌이 공존한다 — 공유 타입 3종(가점), 출결 화면 9종, 점수 규칙 5분류(감점). 감점 체계와 가점 체계가 서로 대응되지 않는다. 화면 표기 코드와 CSV 추출 코드도 다르다. |
| **결정할 것** | 어느 체계로 통일할지 |
| **결정 주체** | 대표진 |
| **바뀌는 것** | 출결 입력·집계·CSV·점수 규칙 전부. **늦어질수록 재작업 범위가 커진다.** |

### 3.3 되돌릴 수 없는 작업의 확인 절차

| | |
| --- | --- |
| **현재** | 설계는 파괴적 액션에 2단 확인 모달과 대상 표시를 요구하지만, 대부분 단일 확인창이거나 확인이 아예 없다. |
| **결정할 것** | 어떤 작업에 어느 수준의 확인을 둘지. 승격 취소를 화면에서 가능하게 할지 |
| **결정 주체** | 대표진 + 백엔드 |
| **바뀌는 것** | 아래 작업들의 실행 동선 |

확인 절차가 **전혀 없는** 작업 — 우선 처리 대상:

| 작업 | 화면 | 영향 |
| --- | --- | --- |

### 3.4 감사 로그의 기록 범위

| | |
| --- | --- |
| **현재** | 계정·권한 관련 작업만 기록된다. 출결 수정, 예외 승인 거절, 콘텐츠 삭제, 최종 합불 확정, 정회원 승격은 남지 않는다. |
| **결정할 것** | 되돌릴 수 없는 작업을 로그에 남길지. 보관 기간·조회 조건 |
| **결정 주체** | 백엔드 + 서비스운영팀 |
| **바뀌는 것** | 감사 로그 화면의 필터·검색 구성. 사고 발생 시 추적 가능 여부 |

관련: 예외 승인 거절 시 사유 기록 없음. 운영지원팀 수정 시 리더가 작성한 원본 사유가 덮어써짐.

### 3.5 데이터 영속성 범위

| | |
| --- | --- |
| **현재** | 백엔드 연동 전이라 모든 변경이 화면을 벗어나면 사라진다. 예외는 점수 규칙(`boaz_score_rules`)·스터디장 안내문 양식(`boaz_delivery_template`)·사전 알림 문구 양식(`boaz_custom_notify_template`) 세 가지이며, 셋 다 브라우저(localStorage)에만 저장된다. |
| **결정할 것** | 브라우저 저장 항목을 서버로 옮길지 |
| **결정 주체** | 백엔드 | 
| **바뀌는 것** | 담당자·기기가 바뀌어도 설정이 유지되는지 |
