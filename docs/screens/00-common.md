## 공통 전제

<!-- SYNC:common-preconditions START — 원본: docs/screens/00-common.md#공통-전제. 수정은 원본에서 하고 grep으로 5개 도메인 문서에 반영한다. -->

> **실제 구현은 현재 백엔드에 이미 구현되어 있는 API 명세를 기준으로 진행한다.**
> 화면에 노출하는 데이터와 등록/수정 등 사용 가능한 동작은 현재 API에서 제공하는 필드와 기능을 우선 기준으로 구성한다.

> **현재 화면은 디자인 확정본이 아니다.** 아직 별도의 UI/UX 디자인 작업은 진행하지 않았으며, PoC 수준으로 대략적인 화면 구조만 구성한 상태이다.
> 실제 디자인 단계에서는 현재 백엔드 API 명세에 맞춰 노출 필드와 등록/수정 동작, 상태 처리 등을 다시 정리하고, 운영진이 조회/등록/수정/삭제할 때 어떤 화면 구성과 작업 동선이 가장 효율적인지 검토한 뒤 최종 디자인을 진행할 예정이다.

> **현재 화면의 데이터는 화면을 벗어나면 유지되지 않는다.** 백엔드 연동 전 PoC이므로 등록·수정 결과는 새로고침 시 초기화된다. 점수 규칙(`boaz_score_rules`)·스터디장 안내문 양식(`boaz_delivery_template`)·사전 알림 문구 양식(`boaz_custom_notify_template`) 세 가지만 브라우저(localStorage)에 저장된다.

> **현재 역할에 따른 화면 노출 제어는 적용되어 있지 않다.** 사이드바는 모든 계정에 동일한 24개 메뉴를 노출한다. 각 문서에 표기된 권한은 [`spec/02-role-model.md`](../spec/02-role-model.md)가 정의한 **의도값**이며, 적용 범위는 [`92-open-items.md`](92-open-items.md)에서 확정한다.

> **현재 화면은 라우터 없이 동작한다.** 화면 전환이 컴포넌트 상태로만 이뤄지므로 개별 화면 URL·딥링크·새로고침 복원·권한 미달 시 403이 성립하지 않는다. 설계 문서의 라우트 맵은 [`91-ia-gap.md`](91-ia-gap.md) §5에서 별도로 다룬다.

## 상태 태그

기능 불릿 끝에 붙이는 고정 어휘다. **이 7개 외의 표현을 쓰지 않는다.** 자유 서술로 상태를 적으면 현황 문서가 결함 목록으로 읽힌다.

| 태그 | 의미 | 상세는 어디에 |
| --- | --- | --- |
| (없음) | 구현 완료. 기본값이므로 표기하지 않는다 | — |
| `진입 경로 미구현` | 화면·모달은 구성되어 있으나 도달할 수 있는 메뉴나 버튼이 없다 | [90](90-screen-inventory.md) |
| `표시만 구현` | 요소는 화면에 있으나 동작이 연결되어 있지 않다 | [90](90-screen-inventory.md) |
| `임시 데이터` | 고정된 예시 데이터로 동작한다. 실제 데이터와 연결되어 있지 않다 | [90](90-screen-inventory.md) |
| `안전장치 필요` | 되돌릴 수 없는 작업인데 확인 절차나 이력이 없다 | [92](92-open-items.md) |
| `확정 필요` | 스펙·IA 결정을 기다리는 중이라 구현이 멈춰 있다 | [92](92-open-items.md) |
| `IA 격차` | 의도된 IA와 위치나 범위가 다르다 | [91](91-ia-gap.md) |
| `API 근거 없음` | 현재 백엔드 API에 대응하는 것이 없다 | [91 §4](91-ia-gap.md) |

**태그는 포인터일 뿐이다.** 화면 섹션에 격차의 종류나 원인을 서술하지 않는다. 설명을 붙이기 시작하면 화면 섹션이 해설로 부풀고 현황 문서가 결함 목록으로 변한다.

`API 근거 없음`을 따로 두는 이유는, 위 공통 전제가 **"실제 구현은 API 명세를 기준으로 진행한다"**고 선언하기 때문이다. 그 선언에 정면으로 걸리는 항목은 다른 격차와 섞이면 안 된다.

`세션 한정`(새로고침 시 소실)은 거의 모든 기능에 해당하므로 개별 태그로 달지 않고 위 공통 전제에서 한 번만 다룬다.

### 사용 예

```markdown
**가능한 기능**
- **공고 등록**  -  새 모집 공고를 만들고 접수 기간과 홍보 책자를 지정한다.
- **회차 생성**  -  주차를 추가하고 명단을 편성한다.  `진입 경로 미구현`
- **최종 합불 확정**  -  지원자의 합격·불합격을 확정한다.  `안전장치 필요`
```

## 서술 원칙

### 화면 목적 (필수, 1문장)

- **쓴다:** `누가` + `무엇을 하기 위해` 여는 화면인지. 주어는 운영진 역할(운영지원팀, 서비스운영팀, 평가자, 스터디장).
- **안 쓴다:** 화면 이름 반복("아카이빙을 관리하는 화면이다"), 컴포넌트·API·상태 이름, 두 문장.
- **판정법:** 이 한 문장만 읽고 "이 화면을 안 열어도 되는 사람은 누구인가"에 답할 수 있으면 합격.

### 화면 구성 (조건부, 2~3문장)

- **쓸 때:** 영역이 2개 이상이거나(목록+상세, 그리드+요약), 탭이 있거나, 읽는 순서가 있을 때. 단순 목록+등록 모달 화면은 생략한다.
- **쓴다:** 화면이 몇 개 영역으로 나뉘고 각 영역이 무엇을 담는지, 사용자가 보는 순서.
- **안 쓴다:** 색·폰트·여백·컴포넌트 라이브러리 이름. 디자인 확정본이 아니라고 선언해놓고 시각 디테일을 서술하면 그 서술이 확정본으로 굳는다.
- **안 쓴다:** 스크린샷을 말로 옮긴 캡션. 이미지가 바로 아래 있으므로 중복이다.

### 가능한 기능 (필수, 불릿)

- **단위:** 1불릿 = 사용자가 취하는 동작 1개. `**동작명**  -  설명 한 문장.` 형태.
- **동작명은 동사로 끝낸다:** `공고 등록`, `합불 확정`. 명사만 쓰면(`공고 상태`) 기능인지 표시인지 구분되지 않는다.
- **쓴다:** 동작의 대상과 결과. 실행 조건이나 권한 제약이 있으면 함께.
- **안 쓴다:** UI 부품 나열("상단에 버튼 3개, 우측에 드롭다운"). 디자인 단계에서 전부 바뀐다.
- **안 쓴다:** 구현 방식(state, 모달, 컴포넌트명). 개발자용 정보는 [`90-screen-inventory.md`](90-screen-inventory.md)로 보낸다.
- **안 쓴다:** 미구현 기능을 구현된 것처럼. 적을 거면 반드시 상태 태그를 붙이고, 태그 없이 적을 바에는 빼는 편이 낫다.
- **개수:** 화면당 3~8개. 2개 이하면 화면을 합칠 후보이고, 9개 이상이면 그 화면이 여러 일을 하고 있다는 뜻이다.

### 공통

- **명명은 운영진 언어를 쓴다.** `부문`, `최종 평가`처럼 실제로 쓰는 말을 쓰고 백엔드 도메인 이름을 그대로 옮기지 않는다. 다만 사이드바 라벨이 이미 그렇게 되어 있는 경우(`(팀장용)`, `(SUBMITTED)`)는 현황 문서이므로 라벨을 그대로 인용하고, 바꿔야 한다는 판단은 `ia/`로 보낸다.
- **의도 IA의 노드 번호를 본문에 쓰지 않는다.** `③ 3.3`, `2.2` 같은 번호는 [`ia/02-ia-tree.md`](../ia/02-ia-tree.md)와 [`91-ia-gap.md`](91-ia-gap.md)에서만 쓴다. 현황 문서가 존재하지 않는 화면의 번호를 인용하면 독자가 그 화면이 있는 줄 안다.
- **역할 이름은 [`spec/02-role-model.md`](../spec/02-role-model.md)를 따른다.** 코드의 `CONTENT_ADMIN` 같은 값이 아니라 운영 조직 이름(서비스운영팀, 운영지원팀, 대표진, 스터디장)으로 쓴다.
- **이미지:** `images/<도메인번호>-<도메인>-<화면번호>-<슬러그>.png`. alt 텍스트는 화면명. 각 이미지 아래 `→ 디자인 작업 예정`을 유지한다.
- **문서 상단 표에 기준 커밋을 박는다.** "현재 화면"이라고 주장하는 문서는 어느 시점의 현재인지 없으면 몇 달 뒤 아무도 믿지 못한다.

## 용어

| 용어 | 뜻 |
| --- | --- |
| BASE / ADV | 정규 활동의 두 단계. BASE는 기초 세션, ADV는 산학 연계·실무 프로젝트 |
| Term | 활동 기간 단위. 방학(1~8주차)과 학기(9~16주차)로 나뉜다 |
| 부문 / 트랙 | 데이터 분석 · 데이터 엔지니어링 · 데이터 시각화 |
| HOST | 출결을 직접 입력하는 스터디장·ADV 팀장 계정. 운영지원팀이 발급하고 기수 말에 회수한다 |
| DRAFT / SUBMITTED | 지원서 작성중 / 제출 완료 상태 |
| 승격 | 최종 합격자를 정회원(MEMBER)으로 전환하는 처리 |
