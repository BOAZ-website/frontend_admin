> 이 페이지는 관리자 페이지 내 **시스템 계정 및 권한 관리 영역의 현재 PoC 구성을 정리한 자료**다. 운영진 계정과 권한 범위를 관리하고, 시스템 내 주요 관리 행위를 확인할 수 있는 구조를 기준으로 정리한다.

<!-- SYNC:common-preconditions START — 원본: docs/screens/00-common.md#공통-전제 -->

> **실제 구현 범위와 화면 구성은 현재 백엔드 API 명세 및 백엔드 협의 결과를 기준으로 확정한다.** 계정 정보, 권한 단위, 변경 가능한 항목, 감사 로그 제공 범위 등은 실제 API에서 제공하는 필드와 동작에 맞춰 구성할 예정이다.

> **현재 화면과 탭 구성은 기획 확정본이 아니다.** 현재는 PoC 수준으로 필요한 기능과 대략적인 구조만 구성한 상태이며, 추후 기획 과정에서 **메뉴 명칭, 탭 구분, 기능의 통합·분리 여부가 변경될 수 있다.**

> **현재 화면의 데이터는 화면을 벗어나면 유지되지 않는다.** 백엔드 연동 전 PoC이므로 등록·수정 결과는 새로고침 시 초기화된다.

> **현재 화면은 라우터 없이 동작한다.** 화면 전환이 컴포넌트 상태로만 이뤄지므로 개별 화면 URL·딥링크·새로고침 복원·권한 미달 시 403이 성립하지 않는다.

<!-- SYNC:common-preconditions END -->

> **이 영역은 예외적으로 역할 분기가 동작한다.** 다른 모든 도메인과 달리, 계정 관리 화면은 로그인 계정이 MASTER인지에 따라 탭 이름과 기능 범위가 달라진다. 다만 그 판정에 쓰이는 역할 타입이 전역 역할 타입과 다르다. → [`spec/02-role-model.md`](../spec/02-role-model.md)

> **현재 상태**
>
> **충족한 요구사항**
> - 운영진 계정 목록 조회, 역할·부서·트랙 필터 및 검색
> - 계정 생성·수정·삭제, 비밀번호 재설정
> - 본인 계정 정보 조회 및 비밀번호 변경
> - 계정 보호 규칙 — 본인 역할 자가 변경 차단, 마지막 SUPER 삭제 차단, 유일 MASTER 삭제 차단, 아이디 중복 차단
> - 역할에 따른 화면 분기 (MASTER는 전체 계정 관리, 그 외는 본인 정보만)
> - 권한 매트릭스 조회
> - 보안 감사 로그 조회
>
> **남은 요구사항**
> - 권한 매트릭스의 성격 확정 — 읽기 전용 참고표인지, 정책을 편집하는 화면인지
> - 전 화면에 역할 기반 접근 제어 적용
> - 역할 타입 일원화 (전역 타입과 이 화면의 타입이 다름)
> - 감사 로그 기록 범위 확대 — 되돌릴 수 없는 작업 전반
> - 감사 로그 보관 기간·조회 조건·검색 기능
> - 회원(User) 관리 — 승격 결과 확인, 기수·부문별 조회
> - 평가자 계정 일괄 생성 흐름 (서류 평가 전 사용)
> - PoC용 역할 전환 장치 제거

## 페이지별 구현 기능

### 1. 운영진 계정 관리 (CRUD)

**화면 목적:** 서비스운영팀장이 운영진 계정을 발급·수정·회수하고, 각 운영진이 본인 계정 정보를 관리하는 화면이다.

**화면 구성:** 로그인 계정에 따라 두 가지로 갈린다. MASTER 계정은 전체 운영진 목록과 계정 생성·수정·삭제 기능이 있는 관리 화면을, 그 외 계정은 본인 정보와 비밀번호 변경만 있는 화면을 본다.

**가능한 기능**

- **운영진 계정 목록 조회**  -  등록된 계정을 아이디·성명·역할·소속 부서·트랙·기수·생성 일시와 함께 확인한다.
- **계정 검색·필터링**  -  역할·부서·트랙 필터와 아이디·이름·부서 검색으로 대상을 좁힌다.
- **운영진 계정 생성**  -  새 계정의 아이디·초기 비밀번호·역할·부서·트랙·기수를 지정해 발급한다.
- **계정 정보 수정**  -  기존 계정의 역할·부서·트랙·기수를 변경한다.
- **계정 삭제**  -  사용하지 않는 계정을 제거한다. 삭제 시 재로그인 토큰이 함께 무효화된다.
- **비밀번호 재설정**  -  운영진의 비밀번호를 새로 발급한다.
- **내 비밀번호 변경**  -  본인 비밀번호를 변경한다. 현재 비밀번호 확인이 필요하다.
- **로그인 시뮬레이션**  -  다른 계정으로 로그인한 상태를 흉내 낸다. (PoC 확인용)  `API 근거 없음`

**적용된 보호 규칙**

| 규칙 | 내용 |
| --- | --- |
| 본인 역할 자가 변경 차단 | 자기 계정의 역할은 스스로 바꿀 수 없다 |
| 마지막 SUPER 삭제 차단 | 시스템에 남은 마지막 SUPER 계정은 삭제할 수 없다 |
| 유일 MASTER 삭제 차단 | 하나뿐인 MASTER 계정은 삭제할 수 없다 |
| 아이디 중복 차단 | 이미 존재하는 아이디로는 생성할 수 없다 |
| 본인 비밀번호 변경 시 현재 비밀번호 확인 | |

> **PoC용 역할 전환 장치를 운영 배포 전에 제거해야 한다.** 이 화면의 "로그인 시뮬레이션"과 헤더의 "계정 전환"은 클라이언트에서 역할을 바꾸는 통로다. 실제 인증을 붙이면서 남겨두면 권한 우회 경로가 된다.

> **오류 메시지에 영문 코드가 그대로 노출된다.** 설계 문서는 에러 코드를 한글 메시지로 매핑하도록 정의하고 있다.  `IA 격차`

### 2. 권한 매트릭스

**화면 목적:** 운영진이 역할별로 어떤 기능을 사용할 수 있는지 비교해 확인하는 화면이다.

**가능한 기능**

- **권한 범위 비교**  -  기능별로 각 역할의 허용·제한 여부를 표로 확인한다.

표의 열은 MASTER · SUPER(대표진/차기) · 서비스운영팀 · 운영지원팀 · 기타 운영진 · HOST 여섯 가지이며, 행은 계정 관리부터 최종 합불까지의 기능 항목이다.

권한 항목의 정본은 [`spec/02-role-model.md`](../spec/02-role-model.md) §2, 기능 × 역할 매트릭스의 정본은 [`spec/01-attendance-system.md`](../spec/01-attendance-system.md) §2-5다. **표를 두 곳에 두면 반드시 어긋나므로 이 문서에는 옮겨 적지 않는다.**

> **현재 이 표는 읽기 전용 참고 자료다.** 여기 적힌 허용·제한이 실제 접근 제어에 사용되지 않는다. 편집 가능한 화면으로 만들지, 참고 문서로 둘지 확정한다.  `확정 필요`

> **표가 9행인 것은 라벨 오류가 아니다.** 스펙의 권한은 10종이며, 화면이 규칙 작성(`RULE_EDIT`)과 규칙 확정(`RULE_ACTIVATE`)을 한 행으로 합쳐 표시하고 있다. 두 권한을 분리할지는 [`spec/02-role-model.md`](../spec/02-role-model.md) §3.3에서 다룬다.

### 3. 보안 감사 로그

**화면 목적:** 운영진이 계정·권한과 관련해 발생한 주요 관리 행위의 이력을 확인하는 화면이다.

**가능한 기능**

- **관리 행위 이력 조회**  -  발생 일시·수행자·작업 유형·대상·상세 내용·IP 주소를 확인한다.

**기록되는 작업 유형:** 계정 생성 · 역할 변경 · 계정 삭제 · 비밀번호 재설정 · 권한 부여

> **계정 관련 작업만 기록된다.** 출결 수정, 예외 승인 거절, 콘텐츠 삭제, 최종 합불 확정, 정회원 승격처럼 **되돌릴 수 없는 작업이 로그에 남지 않는다.** 사고가 발생했을 때 추적할 수단이 없으므로 기록 범위 확대를 검토한다.

> **보관 기간·조회 조건·검색 기능이 정해지지 않았다.** 실제 저장 로그 항목과 조회 조건, 보관 범위는 백엔드와 협의 후 확정한다.  `확정 필요`

## 확정이 필요한 사항

| 항목 | 결정 주체 | 결정되면 바뀌는 것 |
| --- | --- | --- |
| **권한 매트릭스의 성격** — 읽기 전용 참고표인지, 정책을 편집하는 화면인지 | 백엔드 + 서비스운영팀 | 편집 가능이면 저장 API와 검증 규칙이 필요하고, 읽기 전용이면 화면 위치를 문서 영역으로 옮겨야 함 |
| **역할 타입 일원화** — 전역 타입과 이 화면의 타입이 서로 다른 값을 씀 | 백엔드 + 프론트 | 계정 생성·수정 화면의 역할 선택지, 전 화면의 권한 판정 기준 |
| **감사 로그 기록 대상 확대 여부** | 백엔드 + 서비스운영팀 | 기록 항목·보관 기간·조회 조건이 정해져야 화면 설계 가능 |
| **회원(User) 관리 화면 신설 여부** | 서비스운영팀 | 승격 결과 확인과 기수·부문별 조회 경로 |

역할 모델 자체의 결정 사항은 [`spec/02-role-model.md`](../spec/02-role-model.md) §3, 도메인을 가로지르는 안건은 [`92-open-items.md`](92-open-items.md)를 본다.
