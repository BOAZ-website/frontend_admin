# 서류 평가 — 화면·기능 정의

> **2026-11-20 개편 계획:** [서류 평가 개편 — 화면 기획 및 적용 계획](../evaluation-rework-plan.md)에 부문별 메뉴, 상세 이동 오류, 독립 스크롤, 운영진 평가 수정, 승격 API 대조 및 커밋 순서를 정리했다. 구현 전 계획이며 아래 기존 화면 설명과 구분한다.

> 이 페이지는 관리자 페이지 내 **서류 평가 영역의 현재 화면 구성과 기능을 정리한 자료**다. 제출된 지원서를 평가하고, 전체 지원자의 제출 상태를 확인하며, 평가 종료 후 최종 합불 및 정회원 승격까지 관리하는 흐름을 기준으로 구성한다.

> **실제 구현은 현재 백엔드에 이미 구현되어 있는 API 명세를 기준으로 진행한다.**
> 화면에 노출하는 데이터와 등록/수정 등 사용 가능한 동작은 현재 API에서 제공하는 필드와 기능을 우선 기준으로 구성한다.

> **현재 화면은 디자인 확정본이 아니다.** 아직 별도의 UI/UX 디자인 작업은 진행하지 않았으며, PoC 수준으로 대략적인 화면 구조만 구성한 상태이다.
> 실제 디자인 단계에서는 현재 백엔드 API 명세에 맞춰 노출 필드와 상태 처리, 평가 및 최종 합불 동작 등을 다시 정리하고, 평가자와 대표진의 실제 작업 동선을 검토한 뒤 최종 디자인을 진행할 예정이다.

> **현재 화면의 데이터는 화면을 벗어나면 유지되지 않는다.** 백엔드 연동 전 PoC이므로 등록·수정 결과는 새로고침 시 초기화된다.

> **현재 역할에 따른 화면 노출 제어는 적용되어 있지 않다.** 사이드바는 모든 계정에 동일한 메뉴를 노출한다. 이 문서의 권한 표기는 [`spec/02-role-model.md`](../spec/02-role-model.md)가 정의한 의도값이다.

> **현재 화면은 라우터 없이 동작한다.** 화면 전환이 컴포넌트 상태로만 이뤄지므로 개별 화면 URL·딥링크·새로고침 복원·권한 미달 시 403이 성립하지 않는다.

> **현재 상태**
>
> **충족한 요구사항**
> - 제출 지원서 목록 조회, 트랙·최종 판정 필터, 지원자명·대학교·전공 검색
> - 평가 진행 현황 통계 (제출 건수, 내 심사 완료율, 합격·보류·불합격·미결 건수)
> - 지원자 상세 평가 — 인적사항, 지원서 원문, 테이블형 답변 표시
> - 개인 평가 입력(판정 4단계 · 1~10점 · 평가 메모 · 면접 추천 질문)과 저장
> - 저장 시 합격 수·총점 재계산 및 목록 정렬 반영
> - 동료 평가 현황 조회, 면접 추천 질문 모아보기
> - 지원자 간 이전·다음 이동
> - 최종 합격자 목록 조회 및 정회원 승격 실행 (확인 모달 2단 체크)
>
> **남은 요구사항**
> - 최종 합불 확정에 확인 단계와 변경 이력 추가
> - 최종 합불 확정 권한을 대표진(SUPER)으로 제한
> - 미제출(DRAFT) 지원자의 평가·합격 처리 차단 규칙
> - 정회원 승격 취소 경로
> - 승격 부분 실패 시 실패 명단 표시
> - 평가자 신원을 로그인 계정과 연결 (현재는 고정값)
> - 평가 이력 보존 (현재는 덮어쓰기)
> - 지원자 데이터를 리크루팅 영역과 같은 기준으로 연결
> - 지원서 전체 삭제 (시즌 종료 후 개인정보 정리 절차)

> **FE 기능명세 v1.1과 다른 화면 구조 (2026-11-16, 서류 평가 PoC C05)**
>
> - 사이드바 메뉴를 **전체 지원 현황 · 서류 평가 · 합격자 승격** 3개로 줄이고 그룹 제목(지원서 관리·평가 관리·합격자 관리)을 없앴다.
> - 명세의 개인 평가(EVL-MY)와 전체 평가(EVL-GROUP)를 **서류 평가** 화면 하나로 합쳤다. 화면 ID는 `evaluation-my`를 그대로 쓰고, 예전 `evaluation-group` 주소나 마지막으로 연 화면 기록은 서류 평가로 연다.
> - 명세의 전체 평가 상세 모달(평가 현황·지원서 원문·면접 질문)은 지원자 상세 화면으로 옮겼다. 위에 인적사항, 아래 왼쪽에 지원서 답변을 두고, 오른쪽 영역만 **개인 평가 / 평가 현황** 전환으로 바꾼다. 면접 질문은 별도 탭 없이 평가 현황에 평가자별로 붙인다. 평가 현황에는 완료 인원·총점·평균 같은 요약을 두지 않는다.
> - 서류 평가 목록 위의 통계 카드(지원자·제출 완료·임시저장)는 없앴다. 같은 통계는 전체 지원 현황에 있다.
> - 지원자별 최종 판정 변경(REC-ADMIN-18, GROUP-08)은 명세대로 목록 행에서 하고, 상세 탭은 조회 전용이다. 기수 전체 확정·확정 후 잠금은 백엔드 API가 없어 만들지 않는다.

> **부문별 서류 평가 메뉴 (2026-11-20)**
>
> - 서류 평가 메뉴를 **서류 평가** 그룹 아래 **분석 · 시각화 · 엔지니어링** 3개로 나눴다. 화면 ID는 `evaluation-analysis` · `evaluation-visualization` · `evaluation-engineering`이고, 세 메뉴가 같은 평가 목록을 부문만 바꿔 보여 준다. 전체 지원 현황·합격자 승격은 부문 밖 공통 메뉴다.
> - 부문은 메뉴가 정하므로 평가 목록의 트랙 필터를 없앴다. 검색·필터·정렬은 부문마다 따로 남는다. 이전·다음 이동도 그 부문 목록 순서를 따른다.
> - 예전 `evaluation-my`·`evaluation-group` 주소나 마지막으로 연 화면 기록은 분석 메뉴로 연다.
> - 전체 지원 현황 상세의 "평가하기"는 그 지원자 부문의 메뉴로 옮긴 뒤 평가 화면을 연다.
> - 권한 없는 부문 메뉴 숨김은 평가 목 데이터의 평가자가 로그인 계정과 연결되지 않아 평가 API 연동 때 넣는다. 지금은 세 메뉴를 모두 보여 준다.
> - 상세 화면에서 사이드바 메뉴를 누르면(같은 메뉴 재클릭 포함) 상세를 닫고 그 메뉴의 목록으로 간다. 저장하지 않은 평가가 있으면 먼저 확인한다.
>
> **평가 목록 열과 공통 디자인 (2026-11-20)**
>
> - 서류 평가 목록 열은 **이름 · 학교 · 전공 · 합격 · 보류 · 불합 · 총점수 · 개인 평가 · 최종 평가**다. 예전 ‘평가 집계’ 한 열을 판정별 세 열로 나눴다. 개인 평가는 저장 기록이 없으면 ‘미평가’, 미결을 저장했으면 ‘미결’로 구분한다.
> - 목록의 필터·정렬·검색은 출결·전체 지원 현황과 같은 공통 드롭다운(`FilterDropdown`)과 검색칸(`SearchInput`)을 쓰고, 최종 평가 선택은 `SelectDropdown`을 쓴다.
> - 최종 평가는 `FINAL_DECISION_WRITE`가 있으면 행에서 고르는 즉시 저장한다(REC-ADMIN-18 PATCH). 저장 버튼은 없다. 같은 값이면 요청하지 않고, 저장하는 동안 그 행 선택을 잠그며, 실패하면 알림 뒤 이전 값으로 되돌린다. 권한이 없으면 값만 보여 준다.
> - 오류·실패 안내는 브라우저 기본 알림(`window.alert`)으로 띄우고, 저장 성공 같은 완료 안내만 기존 토스트를 쓴다.
> - 합격자 승격 화면에서 API 경로·요청 본문·내부 필드 이름 같은 개발용 문구를 지웠다. API 대조 내용은 [적용 계획](../evaluation-rework-plan.md) §5에 있다.
>
> **지원자 상세 배치와 스크롤 (2026-11-20)**
>
> - 위 인적사항, 아래 왼쪽 지원서 답변·오른쪽 내 평가 배치는 그대로다. 넓은 화면(901px 이상)에서는 상세가 본문 높이를 채우고, 답변과 내 평가가 제목을 남긴 채 각자 스크롤한다. 인적사항은 스크롤하지 않고, ‘평가 저장’ 버튼은 스크롤 밖 아래에 늘 보인다. 좁은 화면은 세로로 쌓고 화면 전체가 스크롤한다.
> - 인적사항 순서는 API 명세(REC-ADMIN-13 ApplicantSummaryResponse) 필드 순서다: 상태 · 이메일 · 전화번호 · 학교 · 전공 · 부·복수전공 · 마지막 학기 · 병역 · 생년월일 · 졸업 예정 · 대학원 진학 계획 · 제출일(부문은 이름 옆 표시). 전체 지원 현황 상세도 같은 순서다.
> - 내 평가 제목 옆에 미평가·저장됨·저장하지 않은 수정 있음을 표시한다.
>
> **운영진 평가 현황 (2026-11-20)**
>
> - 상세 탭 이름은 **개인 평가 / 운영진 평가 현황**이다. 운영진 평가 현황은 오른쪽 좁은 영역 대신 아래 영역 전체 너비를 쓴다. 인적사항과 선택한 지원자는 그대로다.
> - 위에 **합격 · 보류 · 불합 · 총점수**를 보여 준다. 판정 수는 PASS·HOLD·FAIL을 저장한 평가자 수이고, 미평가와 미결은 세지 않는다. 총점은 점수가 있는 평가의 합이다(목록 집계와 같은 `aggregateEvaluations`).
> - 표 열은 평가자 · 판정 · 점수 · 메모 · 면접 추천 질문 · 수정이다. 저장 기록이 없으면 판정 ‘미평가’, 점수 ‘-’이고, 미결을 저장했으면 ‘미결’이다.
> - 본인 행만 수정 아이콘으로 그 행에서 고치고 저장·취소한다. 개인 평가와 같은 입력·검증·저장(REC-ADMIN-17 PUT, 로그인 계정 기준 upsert)을 쓰므로, 저장하면 개인 평가·현황 집계·목록 집계가 함께 바뀐다. 실패하면 알림을 띄우고 입력은 남긴다.
> - 저장하지 않은 입력이 있을 때 탭을 바꾸거나 행 편집을 시작하면 먼저 확인하고, 옮기면 입력을 저장값으로 되돌린다.
> - 수정 아이콘은 지금 본인 행(목 평가자 id 1)이면 보인다. 부문 권한(EVALUATION_OWN_TRACK_WRITE·ALL_TRACK_WRITE) 확인은 평가 API 연동 때 더한다. 서버는 권한이 없으면 저장을 거절한다.
>
> **합격자 부원 등록 (2026-11-20)**
>
> - 메뉴와 화면 제목을 **합격자 부원 등록**으로 바꿨다(화면 ID `evaluation-promote`는 그대로). 상단 지표는 **최종 합격자 · 등록 대기 인원 · 부원 등록 완료**다. 집계는 그대로다. 화면은 위쪽 넓은 요약 영역과 아래쪽 목록 영역 둘로 나뉜다. 요약 영역은 세 지표를 같은 너비로 나란히 두고(제목 아래 인원수, 세 숫자의 글자 크기·굵기·줄 높이 같음) 오른쪽에 ‘완료 / 최종 합격자 수’와 진행 막대를 둔다. 화면 너비가 1024px보다 좁으면 세로로 쌓는다. 목록 영역은 흰 바탕 테두리 상자 하나에 툴바(왼쪽 총 인원, 오른쪽 부문 필터·검색), 표, 하단 선택·등록 줄을 묶는다. 지표 상자 안의 제목·아이콘·설명 문구, 전체 선택·승격 버튼, 확인 모달, ‘회원 상태’ 열을 지웠다.
> - 표 열은 **선택 · 이름 · 부문 · 학교 · 전공 · 이메일 · 연락처 · 총점수 · 상태**다. 대상은 제출 완료이면서 최종 합격인 지원자이고, 분석 → 시각화 → 엔지니어링, 같은 부문은 이름순이다. 부문 필터(전체 / 분석 / 시각화 / 엔지니어링)와 검색을 둔다. 총점수는 운영진 평가 점수 합계이고, 비어 있는 개인정보는 ‘-’다. 표 색·행 높이·구분선은 다른 평가 표와 같고, 짧은 열은 내용에 맞춘 고정 너비, 이메일은 남는 너비를 쓴다(긴 이메일은 줄임표). 이름·학교·전공·이메일은 왼쪽, 나머지는 가운데 정렬이다.
> - 헤더 체크박스는 지금 보이는 행을 모두 고르거나 풀고, 일부만 골랐으면 중간 선택 상태다. 등록 상태와 관계없이 고를 수 있다. 고른 사람이 있을 때만(전체 선택·개별 선택 모두) 목록 상자 아래쪽 줄의 ‘상태’ 열 가운데에 ‘등록하기’ 버튼이, 그 왼쪽에 ‘N명 선택됨’이 보인다. 이 줄은 표의 가로 스크롤 밖에 있다. 행별 등록 버튼은 없다.
> - 등록은 `window.confirm`으로 명단을 확인한 뒤 실행하고, 요청 중에는 다시 실행되지 않는다. 결과는 `window.alert`로 알린다.
> - 상태: 처음은 ‘등록 대기’(화면 초기값이며 서버에서 확인한 회원 상태가 아님), 요청 중 ‘등록 중’, 200 응답에서 `failed_user_ids`에 없는 요청 대상은 ‘등록 완료’, `ALREADY_MEMBER`는 ‘이미 등록’, 그 밖의 오류 코드는 ‘등록 실패’와 사유를 행에 보인다. 5xx·연결 오류는 일부만 처리됐을 수 있어 ‘확인 필요’로 두고, 4xx(권한 없음 등)는 처리되지 않은 것이라 이전 상태로 되돌린다.
> - 요청이 끝나면 ‘등록 실패’·‘확인 필요’ 행만 선택을 남겨 바로 다시 시도할 수 있다. 회원 상태 조회 API가 없어 새로고침하면 행 상태는 ‘등록 대기’로 돌아간다.
> - 행을 누르면 전체 지원 현황과 같은 지원서 상세 창(개인정보 · 답변)이 열린다. 체크박스 클릭으로는 열리지 않고, 닫아도 필터·검색·선택은 남는다. X 버튼, Escape, 바깥 배경 클릭으로 닫힌다(창 안을 누르면 닫히지 않음). 바깥 배경 닫기는 같은 창을 쓰는 전체 지원 현황 상세에도 적용된다. 지원서 삭제 API는 부르지 않는다.
> - 지금은 목 데이터로 동작한다. 요청 body는 로컬 백엔드와 같은 `{ user_ids: [...] }`이고, 요청은 `useEvaluationData`의 `promoteUsers` 한 곳에서 보내므로 API 연동 때 그 안의 목 호출만 바꾼다. 개발 서버 주소에 `?mockScenario=promote-partial`(첫 대상 실패)·`promote-error`(서버 오류)를 붙여 실패를 재현한다.
> - 서류 평가 영역의 화면 문구를 **이름 · 부문 · 학교 · 전공 · 총점수**로 통일했다(지원자·성명→이름, 트랙·합격 부문→부문, 대학교→학교, 본전공→전공, 총점→총점수). API 필드와 내부 enum 이름은 그대로다.

## 페이지별 구현 기능

### 1. 서류 평가 (SUBMITTED)

**화면 목적:** 평가자가 제출된 지원서를 골라 개인 평가를 하고, 여러 평가자의 집계와 최종 판정을 함께 비교하는 화면이다. 명세의 개인 평가 목록과 전체 평가 목록을 합쳤다.

**화면 구성:** 필터·정렬·검색 줄과 지원자 목록 표로 구성된다. 지원자 행을 누르면 지원자 상세 화면이 열린다. 상세에서 목록으로 돌아와도 검색·필터·정렬은 그대로 남는다.

**가능한 기능**

- **지원자 목록 조회**  -  제출 완료 지원서만 트랙·학교/전공·평가 집계·총점·내 평가·최종 판정과 함께 확인한다.
- **필터·검색**  -  내 평가 상태(미평가·저장됨), 최종 판정, 트랙으로 좁히고 이름·이메일·학교·전공으로 검색한다.
- **정렬**  -  제출일 최신순·오래된순, 이름순, 합격 평가 많은순, 총점 높은순.
- **새로고침**  -  목록과 집계를 다시 읽는다.
- **평가 시작**  -  지원자를 골라 상세 화면을 연다. 이전·다음 이동은 지금 목록의 필터·정렬 순서를 따른다.
- **최종 판정 조회**  -  지원자별 최종 판정을 개인 평가 집계와 다른 열로 보여 준다.
- **최종 판정 변경**  -  `FINAL_DECISION_WRITE`가 있는 계정은 행에서 합격·보류·불합격·미결 중 하나를 골라 저장 버튼으로 바꾼다(REC-ADMIN-18). 고른 값이 지금 값과 같으면 저장 버튼이 꺼지고, 저장 중에는 모든 행의 선택·저장을 막는다. 성공하면 "최종 판정이 변경되었습니다." 토스트와 함께 목록을 다시 읽는다. 실패하면 고른 값을 서버 값으로 되돌리고 목록을 다시 읽는다. 네트워크 등 일반 실패는 오류 토스트, 권한 없음·지원서 없음·DRAFT 지원서는 알림 창으로 안내한다. 권한이 없는 계정은 판정 배지만 보인다.

**목록 표시 항목:** 지원자 · 트랙 · 학교 / 전공(여기까지 전체 지원 현황과 같은 이름·표기) · 평가 집계(합격·보류·불합격 수) · 총점 · 내 평가 · 최종 판정. 평가자별 판정·점수·메모·면접 추천 질문은 상세의 평가 현황에서 본다.

**평가 집계 기준:** 평가자별 평가 기록(REC-ADMIN-15)으로 계산하고, 목록과 평가 저장이 같은 계산을 쓴다. 그래서 목록의 집계는 상세의 평가 현황에 보이는 운영진별 기록과 항상 맞는다. 판정 수는 그 판정을 고른 평가자 수, 총점은 평가자별 점수의 합계(내 점수 포함)다. 점수가 없는(null) 평가는 총점에서 뺀다. 평가 기록이 없는 지원자는 평가 집계를 "미평가", 총점을 0점으로 보여 준다.

> **최종 판정 권한은 로그인 계정의 권한 목록으로 판단한다.** 권한 관리 화면과 같은 내 계정 조회(`/api/v1/admin/accounts/me`)의 유효 권한에 `FINAL_DECISION_WRITE`가 있는지 본다. 기본 권한표에서는 대표진·차기대표진만 가진다. 개발 모드의 처음 계정(서비스운영팀장)은 이 권한이 없어 조회만 보이고, 대표진 계정(예: `boaz_president_1`)으로 로그인하면 선택·저장이 보인다. 권한 확인은 화면 편의이며 실제 검사는 서버가 한다. 목 화면에서는 주소에 `?mockScenario=final-decision-error`·`final-decision-denied`·`final-decision-not-found`를 붙여 실패를 재현한다.

> **목 데이터 집계를 기록 기준으로 바꿨다 (2026-11-16).** 목 데이터의 102·103·105 지원자는 평가자별 기록 없이 집계 값만 있어 목록과 평가 현황이 어긋났다. 이제 집계를 기록으로 계산하므로 세 지원자는 0건·0점(미평가)이다. 빠진 기록이나 점수는 만들지 않았다. 실제 API 연동 뒤에는 서버(REC-ADMIN-14)가 집계를 계산한다.

### 2. 전체 지원자 현황 (DRAFT 포함)

**화면 목적:** 운영진이 제출 여부와 관계없이 전체 지원 규모와 제출 진행 상태를 확인하는 화면이다.

**가능한 기능**

- **전체 지원자 목록 조회**  -  작성중(DRAFT)과 제출 완료(SUBMITTED)를 함께 확인한다.
- **제출 상태 확인**  -  지원자별 현재 제출 상태를 구분해 확인한다.
- **지원자 검색·필터링**  -  평가 대시보드와 동일한 조건으로 목록을 좁힌다.

> **평가 대시보드와 같은 화면이고 필터 조건 하나만 다르다.** 여기는 미제출 지원서까지 함께 보여준다.

> **상단 통계와 목록의 기준이 다르다.** 통계 카드는 제출분만 집계하고 목록은 미제출을 포함하므로, 같은 화면에서 두 숫자가 어긋나 보인다. 기준을 통일한다.

> **미제출(DRAFT) 지원자에게도 평가와 합불 처리가 열려 있다.** 제출하지 않은 지원서를 합격 처리하는 것을 막는 규칙이 없다. 허용 여부를 정한 뒤 화면에 반영한다.  `결정됨` → [`spec/04`](../spec/04-evaluation.md) `DASH-02` `DRAFT` 평가 차단

### 3. 지원자 상세

**화면 목적:** 평가자가 지원서 원문을 읽고 개인 평가를 입력하며, 다른 운영진의 평가와 면접 추천 질문을 확인하는 화면이다.

**화면 구성:** 위에서부터 세 단이다.

1. 도구 줄: `← 목록`, 바로 오른쪽에 **개인 평가 / 평가 현황** 전환 버튼, 오른쪽 끝에 현재 위치(`n / 전체`)와 이전·다음 이동. 전환 버튼은 상단 페이지 전환(전체 지원 현황 · 서류 평가 · 합격자 승격)과 같은 모양이다.
2. 인적사항 카드: 이름과 트랙, 그 아래 나머지 항목(전체 지원 현황 상세와 같은 항목)을 여러 열로 모두 펼쳐 보여 준다. 전환과 관계없이 그대로다.
3. 2열: 왼쪽은 지원서 답변(문항별 답변, 테이블형 문항은 표), 오른쪽은 전환에 따라 바뀐다. 두 열은 같은 높이에서 시작하고, 좁은 화면에서는 위아래로 쌓인다.

전환은 오른쪽 영역만 바꾼다. 개인 평가와 평가 현황을 동시에 보여 주지 않는다. 다른 지원자로 옮겨도 고른 쪽이 유지되고, 전환해도 작성 중인 개인 평가는 남으며 확인 창도 뜨지 않는다. 저장하지 않은 평가가 있을 때 다른 지원자나 목록·다른 메뉴로 가면 확인 창을 띄운다.

**가능한 기능**

- **개인 평가**  -  내 평가 입력이다. 판정(합격·보류·불합격·미결, 필수), 점수(1~10점 선택, 비워 둘 수 있음), 평가 의견, 면접 추천 질문을 작성해 저장한다.
- **평가 현황**  -  운영진별 판정·점수·평가 메모·면접 추천 질문을 평가자 단위로 보여 준다(REC-ADMIN-15·19를 평가자 id로 묶음). 로그인한 평가자의 행은 평가자 id로 찾아 맨 위에 둔다. 이름에 '(나)'를 붙이지 않는다(목 데이터 이름의 '(나)'는 떼고 보여 준다). 질문은 복사할 수 있고(성공 "질문이 복사되었습니다." 토스트, 실패 시 오류 토스트), 새로고침할 수 있다. 조회 전용이며 완료 인원·총점·평균 같은 요약은 두지 않는다.
- **지원자 이동**  -  목록 순서대로 이전·다음 지원자로 넘어간다.

평가 현황을 읽지 못해도 개인 평가 입력값은 지워지지 않는다.

**인적사항 표시 항목:** 성명 · 학년/학기 · 대학교 · 본전공 · 복수/부전공 · 병역 여부 · 졸업 예정 · 대학원 진학 · 연락처 · 이메일

> **평가자 신원이 고정값이다.** 로그인 계정과 평가자가 연결되어 있지 않아 "내 평가"와 평가 현황의 본인 행이 실제 로그인 사용자 기준으로 동작하지 않는다(목 데이터의 평가자 id 1). 화면은 평가자 id로만 비교하므로, 인증 연동 때 그 id만 로그인 계정 값으로 바꾸면 된다. 로그인 계정 연동은 후속 작업이다.

> **개인 평가는 덮어쓰기 방식이라 이전 점수·메모가 남지 않는다.** 평가 근거를 소명해야 하는 상황에 대응할 수 없으므로, 이력 보존 여부를 확정한다.  `결정됨` → [`spec/04`](../spec/04-evaluation.md) `DASH-05` 이력 보존

### 4. 합격자 부원 등록

**화면 목적:** 대표진이 서류 평가 이후 최종 합격자를 확인하고 정회원으로 승격 처리하는 화면이다.

**화면 구성:** 상단에 최종 합격자 수·승격 대기 인원·승격 완료 인원을 요약하고, 본문은 합격자 목록 표다. 등록할 사람을 고른 뒤 ‘선택한 인원 등록’을 누르면 브라우저 확인 창(`window.confirm`)에서 명단을 확인하고 실행한다.

**가능한 기능**

- **최종 합격자 목록 조회**  -  최종 판정이 합격인 지원자를 계정 상태·승격 여부와 함께 확인한다.
- **등록 대상 선택**  -  개별 선택하거나 헤더 체크박스로 보이는 행을 모두 선택한다.
- **정회원 승격 실행**  -  선택한 합격자를 정회원(MEMBER)으로 전환한다.  `결정됨` → [`spec/04`](../spec/04-evaluation.md) `PROM-03` 확인(인원·명단·비가역)은 `window.confirm`으로 대신한다, 취소 기능 없음
- **승격 현황 확인**  -  승격 완료·대기 인원을 구분해 확인한다.

**목록 표시 항목:** 선택 · 이름 · 부문 · 학교 · 전공 · 이메일 · 연락처 · 총점수 · 상태 (2026-11-20 개편, 위 ‘합격자 부원 등록’ 기록 참고)

승격 시 서버가 각 지원자의 최신 제출 지원서에서 이름·전화번호·대학교·전공을 회원 정보로 복사하고 회원 유형을 정회원으로 변경한다. 개별 트랜잭션으로 처리되어 부분 성공을 허용한다.

> **이 시스템에서 가장 되돌리기 어려운 작업이다.** **등록을 취소하는 경로가 화면에 없다.** 현재 방어책은 실행 전 확인 창뿐이다. 오처리 시 대응 절차를 백엔드와 함께 확정한다.

> **부분 실패는 행 상태로 표시한다(2026-11-20).** 실패한 사람은 ‘등록 실패’와 사유, 결과를 알 수 없으면 ‘확인 필요’로 보인다. 다만 회원 상태 조회 API가 없어 새로고침 뒤에는 결과가 남지 않는다.

> 설계 문서는 이 화면을 **결과 처리** 단계로 정의하고 `CSV 추출 → 합격자 승격 → 지원서 전체 삭제`를 한 화면에 순서대로 두도록 했다. 현재는 CSV 추출이 리크루팅 영역으로 분리되어 있고 지원서 전체 삭제는 구현되어 있지 않다.  `IA 격차`
