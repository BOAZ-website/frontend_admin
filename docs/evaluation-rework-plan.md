# 서류 평가 개편 — 화면 기획 및 적용 계획

작성일: 2026-11-20. 상태: 구현 진행 중. 6절의 커밋 순서대로 적용한다.

## 1. 범위와 결정 상태

사용자 요청은 시스템·계정 및 출결 화면과 디자인 통일, 서류 평가 이모지 제거, 브라우저 뒤로가기, 지원서 답변·내 평가 독립 스크롤, 개인정보 순서 보존, 부문별 메뉴 분리, 지원자 상세 내 운영진 평가 현황 전환, 본인 평가 수정, 합격자 승격 API 적용이다. 상세 화면에서 사이드 메뉴로 이동하지 못하는 오류도 함께 해결한다.

| 구분 | 내용 |
| --- | --- |
| 요청 확정 | 대제목 ‘서류 평가’, 분석·시각화·엔지니어링 메뉴 분리, 기존 내부 화면 재사용 |
| 요청 확정 | 지원자 상세에서 개인 평가 / 운영진 평가 현황 전환. 현황 사이드 메뉴는 만들지 않으며 본인 기록만 수정 |

| 요청 확정 | 직접 만든 안내 모달 대신 브라우저 기본 alert, 이동 확인은 confirm 사용 |
| 요청 확정 | 전체 지원 현황과 합격자 승격은 부문 밖 공통 메뉴. 기존 서류 평가 표만 분석·시각화·엔지니어링으로 분기 |

## 2. 코드에서 확인한 사실

### 2.1 상세 화면에서 다른 메뉴로 이동하지 못하는 원인

- `src/app/App.tsx`는 서류 평가 메뉴들에 같은 `EvaluationManagePage`를 유지하고 `initialTab`만 바꾼다.
- `EvaluationManagePage.tsx`의 `initialTab` effect는 `mainTab`만 변경한다. `selectedApplicant`는 초기화하지 않는다.
- 같은 파일의 `if (selectedApplicant) return ...`이 목록·승격 화면보다 먼저 실행된다. 따라서 사이드 메뉴 선택은 바뀌어도 상세가 계속 보인다.
- `App.tsx`는 메뉴 주소를 `replaceState`로 덮어쓴다. `hashchange`는 처리하지만 상세 진입은 주소에 기록하지 않으며, 이 이벤트에서 이탈 확인도 하지 않는다. 현재 구조로는 정상적인 목록→상세→뒤로가기 이력을 만들 수 없다.

해결: 메뉴·부문·목록/상세를 하나의 화면 위치 상태로 관리한다. 이동 승인 후 상세 선택, 입력 초안, 오류, 이전·다음 목록을 정리하고 진행 중 조회의 요청 번호를 무효화한다. 같은 메뉴 재클릭도 상세에서 목록으로 이동하는 명시적 동작으로 처리한다. 단순 `key` 변경으로 전체를 다시 만들면 목 데이터 저장값까지 소실될 수 있으므로 피한다.

### 2.2 최종 판정 저장 버튼

- `MyEvaluationList.tsx`의 `finalDrafts`는 선택한 값을 임시 보관하고 저장 버튼에서 `onSaveFinalDecision`을 호출한다.
- 로컬 백엔드에는 `PATCH /api/v1/admin/recruitment/applicants/{applicantId}/final-decision`이 있다. HTTP 변경 요청이 필요하다는 사실은 별도 저장 버튼이 필요하다는 뜻이 아니다.
- 제안: 선택 완료 시 요청하고 해당 행에 저장 중 표시, 성공 시 서버 값 반영, 실패 시 이전 값 복원과 안내. 동일 값은 재요청하지 않는다. 연속 변경과 늦은 응답의 덮어쓰기를 막는다.
- `FINAL_DECISION_WRITE` 권한과 제출 완료 조건은 유지한다. ‘내 평가 저장’은 여러 입력을 묶어 저장하므로 별도 버튼을 유지한다.

### 2.3 본인 평가 수정 API

로컬 `../backend/src/main/java/com/boaz/backend/domain/recruitment/controller/ApplicantEvaluationAdminController.java`에 다음 API가 구현되어 있다.

| 용도 | API | 확인 내용 |
| --- | --- | --- |
| 내 평가 조회 | `GET /api/v1/admin/recruitment/applicants/{applicantId}/evaluations/me` | 없으면 `data: null` |
| 내 평가 생성·수정 | 같은 경로의 `PUT` | 로그인 계정의 평가를 upsert. 별도 수정 API 불필요 |

`RecruitmentService.saveMyEvaluation`은 로그인한 관리자 ID로 저장한다. `EVALUATION_OWN_TRACK_WRITE` 또는 `EVALUATION_ALL_TRACK_WRITE`가 필요하며, 전 부문 권한이 없으면 본인 부문만 가능하다. 화면에서 본인 행인 것만으로 수정 가능하다고 판단하지 않고 부문 권한도 함께 확인한다. 타인의 관리자 ID를 요청으로 보내는 편집은 만들지 않는다.

확인 범위는 로컬 백엔드 소스이며 배포 서버 버전·실제 인증 연동은 별도 검증해야 한다.

## 3. 화면 구조안

```text
전체 지원 현황 (공통)
서류 평가
├─ 분석 → 기존 서류 평가 표(분석) → 개인 평가
├─ 시각화 → 기존 서류 평가 표(시각화) → 개인 평가
└─ 엔지니어링 → 기존 서류 평가 표(엔지니어링) → 개인 평가
합격자 승격 (공통)
```

사용자 답변으로 공통 메뉴와 부문 분리를 확정했다. 각 부문 안에 전체 지원 현황·승격 탭을 다시 만들지 않는다. 지원자 상세에서 ‘개인 평가 / 운영진 평가 현황’을 전환한다. 운영진 평가 현황의 독립 사이드 메뉴와 별도 지원자 목록은 만들지 않는다.

- `widgets/sidebar/model/navigation.ts`의 출결과 같은 section/groups/pages 구조 및 `Sidebar.tsx` 렌더러를 재사용한다. 화면을 부문별로 복사하지 않고 공통 화면에 `track`을 전달한다.
- `ActivePage`, 페이지 제목, 유효 페이지 검사, 기존 해시 주소 호환 처리를 함께 수정한다. 메뉴에 들어온 부문을 목록·검색·집계·상세·이전/다음 모두에 적용한다.
- 분석·시각화·엔지니어링 메뉴의 부문 필터는 제거한다. 공통 전체 지원 현황은 조회 가능한 부문이 여럿일 때 부문 필터를 제공한다. 상세 현황에는 별도 부문 필터를 추가하지 않으며 승격 개편은 보류한다.
- 전체 지원 현황은 DRAFT 포함, 서류 평가는 SUBMITTED만, 승격은 SUBMITTED + PASS를 유지한다.
- 부문 간 이동해도 각 목록의 검색·정렬을 보존하되, 다른 부문의 지원자와 선택 상태가 섞이지 않게 한다.
- 메뉴 노출과 API 접근 권한은 별개다. 서버가 허용하는 조회·수정 범위를 따른다.

### 3.1 개인 평가 화면

기존 배치를 유지한다. 상단 개인정보, 하단 왼쪽 지원서 답변·오른쪽 내 평가를 유지하며 3열로 변경하지 않는다. 개인정보에는 별도 내부 스크롤을 만들지 않는다.

- 하단 답변·내 평가 패널에 제목과 독립 스크롤 영역을 둔다. 남은 화면 높이를 사용하는 부모와 `min-height: 0`, `overflow-y: auto`를 조합한다.
- 개인정보는 입력칸처럼 보이는 상자들을 나열하지 않고, 라벨은 작은 보조 글자·값은 본문 글자로 표시하는 `dl`을 쓴다. 긴 이메일·학교·전공은 줄바꿈하며 값 누락은 `-`로 통일한다.
- 항목 순서를 바꾸는 임의 그룹 분류는 하지 않는다. 현재 `applicantInfoFields`의 고정 순서를 API 명세의 필드 나열 순서와 대조해 바꾼다. 내부 식별자 등 개인정보 표시 대상이 아닌 필드를 제외해도 남은 필드의 상대 순서는 유지한다.
- JSON 객체의 실행 시 키 순서에 의존하지 않고 명세 순서를 명시한 필드 배열을 한 곳에서 관리한다. 개인정보 순서와 지원서 문항 답변 순서는 별개이며 답변은 서버의 문항 순서를 유지한다.
- 답변의 문항 번호·표·줄바꿈을 유지한다. 개인정보 값이 길어도 답변 패널 너비를 밀어내지 않게 한다.
- 내 평가 저장 영역은 접근하기 쉬운 위치에 유지하며 저장 중·오류·수정 여부를 표시한다.
- 좁은 화면은 순서대로 세로 배치하거나 패널 전환을 제공한다. 두 영역의 독립 스크롤을 무리하게 좁은 화면에 강제하지 않는다. 키보드 포커스로 각 스크롤 영역에 접근 가능해야 한다.

### 3.2 운영진 평가 현황 — 상세 내 전환 방식 확정

부문별 지원자 표에서 지원자를 선택한 뒤 상세의 **개인 평가 / 운영진 평가 현황** 버튼으로 전환한다. 지원자 선택과 상단 개인정보는 유지한다. 개인 평가에서는 하단 왼쪽 답변·오른쪽 내 평가를 표시하고, 현황에서는 하단 전체 너비를 운영진 평가 표로 사용한다. 오른쪽 좁은 패널만 바꾸는 기존 방식은 변경한다.

- 대표진 등 전 부문 평가 권한 보유자는 분석·시각화·엔지니어링 메뉴에서 지원자를 선택한다. 본인 부문 권한만 가진 운영진에게 다른 부문 메뉴를 숨긴다. 직책 이름 대신 유효 권한으로 판단하며 서버 권한 검사도 유지한다.
- 기존 `EvaluatorResultsTab`의 평가 기록·면접 질문·복사 로직을 재사용한다. 별도 현황 사이드 메뉴, 현황용 지원자 목록, 현황 전용 부문 필터는 추가하지 않는다.
- 선택한 지원자에게 남겨진 대표진·타 부문 평가 기록도 임의로 제외하지 않는다. 백엔드가 반환하는 현재 평가 가능자와 기존 평가자의 합집합을 표시한다.

**상단 집계와 평가자별 표시**

| 위치 | 표시 내용 | 계산·표시 기준 |
| --- | --- | --- |
| 현황 상단 | 합격 / 보류 / 불합 / 총점 | 선택한 지원자의 저장된 운영진 평가 기준. 기존 공통 카드 디자인 재사용 |
| 평가자별 표 | 평가자 / 판정 / 점수 / 메모 / 면접 추천 질문 / 수정 | 본인 행을 맨 위에 둠(이름에 `(나)` 표시 없음), 다른 운영진은 조회만 가능 |
| 미평가 | 판정 `미평가`, 점수 `-` | 저장된 평가 기록이 없음 |
| 저장된 평가 | 저장한 판정과 점수 | PENDING은 `미결`로 표시하며 미평가와 구분 |
| 점수 없음 | `-` | 점수가 null인 저장 기록도 포함 |
| 총점 | 저장된 점수 합계 | 본인 점수 포함, null 제외. 합계가 0이면 `0` 표시 |

합격·보류·불합 수는 각각 PASS·HOLD·FAIL을 저장한 평가자 수다. 미평가와 PENDING은 세 판정 수에 넣지 않는다. 저장 여부를 점수나 판정 수 합계가 0인지로 추론하지 않는다. 값 0과 null을 구분해 렌더링하되, 이 표시 규칙이 현재 입력 허용 범위(1~10점)를 0점까지 확대하는 것은 아니다.

상단 집계 추가는 **지원자 상세의 운영진 평가 현황**에만 해당한다. 이전에 제거하기로 한 전체 지원 현황의 통계 카드 6개를 복원하지 않는다.

**본인 행 수정과 데이터 갱신**

- 본인 행이고 수정 권한이 있으면 그 행에 기존 공통 수정 아이콘을 표시한다. 누르면 같은 행에서 편집하고 저장/취소로 종료한다. 판정·점수·메모·면접 질문은 개인 평가와 같은 데이터 및 검증·저장 로직을 사용한다.
- 저장 전 초안은 다른 화면의 저장값에 반영하지 않는다. 취소하면 원래 값으로 돌아간다. 기존 PUT 요청에 필요한 필드를 함께 보내며 수정하지 않은 값은 보존한다.
- 저장 성공 후 개인 평가, 현황 행, 현황 상단 집계·총점, 지원자 목록의 집계·총점이 함께 갱신된다. 같은 집계 함수를 재사용하고 필요 데이터는 재조회한다.
- 저장 실패 시 입력값을 유지하고 브라우저 기본 경고창으로 안내한다. 미저장 상태에서 탭·지원자·메뉴 이동 시 기본 confirm으로 확인한다.
- 검증: 미평가, 저장된 미결, 점수 null, 총점 0, 판정 변경, 점수 변경, 저장 실패 시 집계 유지, 세 화면 간 값 일치.

### 3.3 디자인 통일과 이모지

평가 목록의 기존 ‘평가 집계’ 한 열을 **합격 / 보류 / 불합** 세 열로 나누고, 이어서 **총점 / 개인 평가 / 최종 평가**로 표시한다. 제공 이미지는 컬럼 구성 참고이며 색상·배지·표·드롭다운 디자인은 현재 시스템 공통 디자인을 재사용한다. 최종 평가는 권한이 있을 때 공통 드롭다운으로 즉시 저장하고, 없으면 값만 표시한다. 미평가(null)와 저장된 미결(PENDING)은 이미지와 무관하게 데이터 의미를 구분한다.

- 기준: `shared/ui/systemStyles.ts`의 표·행·버튼·입력 스타일과 `Btn`, `FormDialog`, `FilterDropdown`, `SearchInput`, `SplitView`의 실제 사용 예시.
- 표 머리·행 높이·구분선·정렬·호버·선택·빈 상태와 수정/저장/취소 버튼을 시스템·출결과 맞춘다. 이미 맞춘 부분은 재사용한다.
- `app/styles/review-design.css`의 광범위한 색상·버튼 덮어쓰기가 공통 스타일을 무력화하는지 정리한다. 전역 시스템·출결 화면에는 의도치 않은 변경이 없어야 한다.
- 서류 평가의 실제 표시 텍스트와 목 데이터 안내에서 이모지를 제거한다. 현재 큰 이모지 범위 검색에서는 결과가 없었으므로 렌더링된 UI 및 기호도 점검한다. `←`, `↻` 같은 문자 아이콘은 필요하면 기존 lucide 아이콘으로 통일한다. 기능성 SVG 아이콘 전체 삭제로 확대하지 않는다.
- 승격 화면의 PATCH·API 경로·트랜잭션 설명은 개발 문서로 옮기고 사용자에게는 대상·결과·실패 사유를 보여 준다.

## 4. 화면 이동 및 뒤로가기 설계 — 후순위

메뉴 클릭 시 상세가 남는 오류는 이번 우선 작업이다. 아래 브라우저 이력 개편은 별도 후속 작업으로 미루며 현재 메뉴 수정의 선행 조건으로 삼지 않는다.

1. 메뉴, 부문, 내부 탭, 지원자 ID를 URL/히스토리와 일치시키는 공통 이동 함수를 만든다. 초안·개인정보 본문은 URL에 넣지 않는다.
2. 사용자가 새 화면으로 이동할 때 이력을 추가한다. 초기 주소 정규화·옛 주소 호환에는 replace를 사용한다. 뒤로/앞으로 복원 중에는 이력을 다시 추가하지 않는다.
3. 브라우저 뒤로가기·앞으로가기, Alt+Left/Right, 지원하는 환경의 터치패드 제스처 및 마우스 뒤로가기 버튼이 같은 히스토리를 사용하게 한다. 제스처 자체를 가로채는 별도 휠 핸들러는 만들지 않는다.
4. 입력 변경이 있으면 이동 전에 한 번만 확인한다. 취소 시 URL·메뉴 선택·지원자·초안·스크롤이 그대로 유지되도록 복원한다. 입력 중 Backspace를 전역 뒤로가기 키로 연결하지 않는다.
5. 저장 중 이동, 늦은 조회/저장 응답, 지원자 삭제·접근 거부, 직접 상세 주소 진입 시 목록 복귀를 정의한다. 새로고침·창 닫기는 dirty 상태에서 브라우저 기본 `beforeunload` 경고를 사용한다.

## 5. 합격자 승격 API 대조와 화면 기획 — 보류

사용자 결정에 따라 아래는 조사 기록으로만 보존한다. 현재 작업에서 승격 API 연동이나 화면 재기획을 진행하지 않는다. 기존 공통 승격 메뉴의 위치와 메뉴 이동 버그만 유지·정리한다.

### 5.1 확인된 계약과 차이

사용자가 제공한 명세는 `PATCH /api/v1/admin/users/promote`, 순차 개별 트랜잭션, 비즈니스 오류 skip, 500 즉시 중단, 실패 목록 반환이다. 로컬 `UserAdminController`, `UserAdminService`, DTO 및 컨트롤러 테스트에서 다음 차이를 확인했다.

| 항목 | 적용 기준 또는 확인 필요 |
| --- | --- |
| 권한 | 로컬 구현은 `MEMBER_PROMOTION_WRITE` 필요. 단순 Admin 여부보다 구체적 |
| 요청 JSON | 제공 명세는 `userIds`. 로컬 프로파일은 SNAKE_CASE이고 컨트롤러 테스트는 `{ "user_ids": [1, 2] }` 사용. 실제 서버 계약을 확인한 뒤 API 어댑터 한 곳에서 매핑 |
| 응답 | `data.failed_user_ids`, 각 항목 `user_id`, `error_code`. 성공 ID 배열은 응답에 없음 |
| 대상 | SUBMITTED 지원서와 PASS 최종 판정 필요. 로컬 구현은 `APPLICANT_NOT_PASSED` 오류도 반환 |
| 복사 필드 | 로컬 구현은 이름·전화·대학·전공·부문·기수 외 이메일, 부복수전공, 학기, 병역, 생년월일, 졸업 예정, 대학원 계획도 복사 |
| 복수 지원서 | 조회가 `userId + SUBMITTED`의 단건 Optional이며 최신순 조건과 모집 ID가 없음. ‘최신 지원서를 자동 선택’한다고 안내하지 말 것. 여러 기수 지원 가능 시 BE 정책 확인 |
| 승격 상태 조회 | 현재 FE `is_promoted_to_member`는 목 데이터. 지원자 응답의 회원 상태 또는 User 조회 조합으로 영속적인 확인이 가능한지 확인 필요 |
| 회원 명단 연계 | 출결 문서에는 회원 마스터 생성 연계 요구가 있으나 확인한 서비스는 User 변경. member 생성·반기 등록이 자동으로 된다고 안내하지 않으며 별도 계약 확인 |

기존 프론트는 `useEvaluationData`에서 목 함수를 호출한다. API 경로가 화면에 적혀 있어도 실제 연동 완료가 아니다. 목 저장소와 실서버 승격을 섞지 않고 실 ID·권한·조회 소스를 먼저 정합하게 연결한다.

### 5.2 화면 흐름

1. 모집 기수와 부문을 확인한다. SUBMITTED + PASS 대상 목록을 표시한다.
2. 선택 / 이름 / 부문 / 이메일 / 대학·전공 / 회원 상태를 표시한다. 필요한 경우 user ID를 보조 정보로 제공한다. 이미 회원인 사람은 선택 불가로 표시한다.
3. 검색·필터로 보이는 승격 가능 인원만 전체 선택한다. 모집·부문 변경 시 기존 선택을 초기화한다. 전송 전 user ID를 중복 제거하고 현재 대상 여부를 검증한다.
4. ‘선택한 N명 승격’ → 대상 명단·기수·부문·회원 전환 내용을 확인하는 다이얼로그 → 실행. 되돌리는 기능이 없다는 점을 간결하게 안내한다.
5. 실행 중 중복 요청을 막고 `try/catch/finally`로 로딩을 해제한다. 화면 이동으로 요청이 취소돼도 서버 작업이 취소됐다고 간주하지 않는다.
6. 200 전체 성공: 대상 상태 재조회, 선택 해제, 완료 안내.
7. 200 부분 성공: 이번 요청 ID에서 실패 ID를 제외한 집합을 성공으로 계산하고, 이름·실패 사유·후속 조치를 표로 남긴다. 상태 재조회 후 재시도 가능한 실패만 선택한다.
8. 500 또는 연결 종료: ‘처리 결과를 확인할 수 없습니다. 일부 대상은 승격되었을 수 있습니다’로 안내한다. 전체 롤백·전체 실패라고 표시하지 않는다. 상태를 재조회한 뒤 미처리자만 재시도한다. 상태 조회가 없다면 안전한 재시도 UX가 구현되지 않은 의존성으로 남긴다.

| 오류 | 화면 처리 |
| --- | --- |
| USER_NOT_FOUND | 존재하지 않는 계정, 대상 재조회 |
| APPLICATION_NOT_FOUND | 제출 완료 지원서 없음, 대상에서 제외하고 재조회 |
| ALREADY_MEMBER | 이미 회원임을 표시하고 재시도 제외. 이번 요청의 신규 성공 인원에는 포함하지 않음 |
| APPLICANT_NOT_PASSED | 최종 합격 아님, 판정 재조회 후 대상 제외 |
| 400 | 빈 목록·잘못된 ID 등 입력 오류 안내 |
| 401 / 403 | 공통 인증·권한 처리, 성공으로 갱신하지 않음 |
| 500 / 네트워크 | 결과 불명 상태와 재조회 제공, 자동 일괄 재전송 금지 |

지원서 삭제는 별도 REC-ADMIN-010 작업이다. 승격 성공 후 자동 호출하지 않는다. CSV 추출이나 기수 전체 판정 확정을 이 API의 필수 선행 조건으로 임의 추가하지 않는다.

## 6. 커밋 및 구현 순서

문서 → 이동 오류 수정 → 부문 메뉴 분리 → 공통 디자인·평가 표 컬럼 → 기존 상세 배치 정리 → 최종 판정 즉시 저장 순으로 진행한다. 운영진 평가 현황은 상세 내 전환·넓은 표·상단 집계·본인 행 편집으로 구현하며, 오류 및 이동 확인은 브라우저 기본 alert/confirm으로 연결한다. 브라우저 이력은 후순위, 승격 신규 작업은 보류한다.

| 순서 | 커밋 제목 제안 | 범위 / 완료 기준 |
| --- | --- | --- |
| 0 | `docs(evaluation): 서류 평가 개편 및 승격 적용 계획 정리` | 본 문서와 기존 명세 연결, 확정/미정/충돌 분리 |
| 1 | `fix(evaluation): 메뉴 이동 시 개인 평가 상세 상태 정리` | initialTab 변화·같은 메뉴 재클릭·초안 확인·비동기 요청 무효화. 상세에서 원하는 메뉴로 실제 이동 |
| 2 | `feat(evaluation): 부문별 메뉴와 접근 범위 구성` | 공통 화면에 track 주입, 부문 필터 제거, ActivePage/제목/옛 주소 처리. 브라우저 이력 개편 제외 |
| 3 | `style(evaluation): 시스템 출결 공통 표와 버튼 적용` | 공통 스타일 재사용, 이모지·개발자 안내 정리, 이미 반영된 스타일 유지 |
| 4 | `feat(evaluation): 개인 평가 기존 배치와 답변 입력 스크롤 개선` | API 명세 필드 순서 반영, 의미 있는 라벨/값 배치, 답변·입력 독립 스크롤, 작은 화면 대응 |
| 5 | `feat(evaluation): 상세 평가 현황 집계와 본인 행 수정 제공` | 상세 내 전환, 전체 너비 표, 판정 수·총점, 미평가 구분, 본인 수정 및 개인 평가·목록 동기화 |
| 6 | `feat(evaluation): 최종 판정 선택 즉시 저장` | 적용 확정. 저장 표시·동일 값 생략·실패 복원·권한 유지 |
| 보류 7a | `feat(evaluation): 합격자 승격 API와 결과 처리 연결` | JSON 키·인증·대상 조회 계약 확정 후 어댑터 및 목 계약 일치, 부분 성공·불명 결과 처리 |
| 보류 7b | `feat(evaluation): 합격자 승격 확인 및 실패 재처리 화면` | 대상 선택·확인·권한·결과 표·실패자 재시도, API 기술 문구 제거 |

각 커밋에는 해당 기능의 명세 변경과 필요한 검증을 함께 넣는다. 실제 git commit·push는 이 계획 작성에 포함하지 않는다.

## 7. 검증과 문서 정합성

- 이동: 상세에서 전체 현황/승격/다른 부문/현재 메뉴 재클릭, 미저장 확인 취소와 승인, 뒤로/앞으로, 늦은 응답, 저장 중 이동.
- 필터: 부문 범위 유지, DRAFT는 평가·승격 제외, 동일 사용자 ID 중복 방지, 목록 순서와 이전/다음 일치.
- 화면: 긴 개인정보·긴 답변·표 답변, 독립 스크롤, 키보드 접근, 작은 화면, 시스템·출결 스타일 회귀.
- 본인 수정: 본인/타인, 본인 부문/타 부문, 미평가/기존 평가, 조회·저장 오류, 저장 후 집계 갱신.
- 승격: 전체 성공/부분 성공/모두 실패/ALREADY_MEMBER/미합격/빈 선택/중복 클릭/권한 없음/중간 500/새로고침 후 상태 확인.
- 구현 시 기존 의미 있는 모델 테스트와 회귀 테스트를 실행하고 타입 검사·lint·build를 확인한다. 단순 스타일 변경에 구현을 그대로 복제한 테스트는 추가하지 않는다.
- 기존 `docs/spec/04-evaluation.md`의 기수 전체 확정·APPLICANT→MEMBER·기수당 1회 승격 등은 현재 API에 그대로 적용할 수 없다. 실제 값은 OUTSIDER→MEMBER이며 실패 후 재실행을 지원한다. 기능 확인 없이 과거 기획을 백엔드 구현 사실로 취급하지 않는다.
- `docs/screens/03-evaluation.md`, `docs/ia/02-ia-tree.md`, FE WBS는 구현되는 커밋에서 최종 구조로 갱신한다. 현 문서의 기존 구현 설명을 계획만으로 완료 처리하지 않는다.

## 8. 구현 전 남은 확인

사용자 답변 반영 완료: 공통 전체 지원 현황·승격, 세 부문 평가 목록(권한별 숨김은 평가 API 연동 때), API 명세 순서의 개인정보, 기존 상세 배치 유지, 최종 판정 즉시 저장 및 실패 복원. 운영진 현황은 독립 메뉴 대신 상세 내 전환으로 확정했으며 상단 판정 수·총점, 미평가 구분, 본인 행 편집 및 데이터 동기화를 포함한다. 안내는 기본 alert, 이동 확인은 confirm이다. 뒤로가기는 후순위, 승격 신규 작업은 보류한다.

백엔드 확인: 배포 버전, 승격 요청의 userIds/user_ids 계약, 지속 가능한 회원 상태 조회, 복수 모집 지원서 선택 정책, 회원 마스터 생성 연계. 평가 수정 API 존재 여부는 로컬 소스에서 확인 완료했다.

## 9. 브라우저 기본 경고창 — 확정

직접 만든 안내·오류 모달을 없애고 브라우저 기본 `window.alert()`로 오류·처리 결과를 안내한다. 미저장 상태에서 이동할 때는 `window.confirm()`을 사용한다. 별도 디자인 모달과 토스트를 새로 만들지 않는다. 검증, 저장 실패 시 입력 보존, 최종 판정 실패 시 값 복원, 조회 재시도와 빈 상태 등 기능 처리 자체는 유지한다. 시스템 처리 수단은 더 이상 미정이 아니다.

기존 토스트는 성공 안내(‘평가가 저장되었습니다.’ 등)에만 남기고, 오류·실패 안내는 모두 `window.alert()`로 바꾼다. 부문별 평가 목록에서는 부문이 정해지므로 ‘트랙’ 열을 표시하지 않는다.
