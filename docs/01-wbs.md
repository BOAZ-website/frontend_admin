## 이 문서를 읽는 세 층

이 WBS는 세 가지가 다른 일을 한다. 섞어 읽으면 "티켓 다 닫았는데 왜 안 끝났지"가 된다.

| 층 | 무엇 | 언제 보나 |
| --- | --- | --- |
| **티켓** | EPIC이 담는 작업 단위. 규모 태그와 담당(`F` 프론트 / `B` 백엔드)이 붙는다 | 매일 — 진척 추적 |
| **시나리오 A/B/C** | 흐름이 끊김 없이 이어지는가. **EPIC 완료 게이트** | EPIC 닫기 직전 — 마지막 관문 |
| **마일스톤 M0~M6** | 여러 EPIC을 관통하는 일정 지점 | 커트라인 맞추는지 잴 때 |

**EPIC은 "티켓 전부 close 그리고 담당 시나리오 통과"라야 닫힌다.** 티켓만 닫고 흐름이 끊기면 EPIC은 열려 있다. 티켓 소진은 진척이고, 시나리오 통과가 완료다.

**부분 통과는 EPIC 닫힘과 다른 상태다.** 커트라인 B의 목업 리허설처럼 시나리오 일부를 축소 조건으로 통과하는 경우가 있다. 그것은 "리허설 판정 통과"이고 EPIC은 여전히 열려 있다. 시나리오 A에 리허설 판정과 실전 판정 두 단을 둔 이유다.

## 먼저 알아야 할 사실 세 가지

### 화면은 24개인데 통신 코드는 0줄이다

`src` 전체에서 `fetch` · `axios` · 쿼리 훅 호출이 한 건도 없다. 코드에 보이는 `/api/v1/admin/...` 문자열은 전부 화면에 찍는 텍스트일 뿐 호출되지 않는다. 런타임 의존성도 `react` · `react-dom` · `lucide-react` · `tw-animate-css` 네 개가 전부라 HTTP 클라이언트 · 서버 상태 관리 · 라우터 · 폼 · 스키마 검증이 모두 없다.

**그래서 앞으로 할 일은 연동이 아니라 데이터 계층을 0에서 세우는 것이다.** 화면 뼈대(24개 컴포넌트)는 src에 있지만, **데이터 계층 뼈대는 없다.** 이 데이터 계층 뼈대가 5개 도메인 EPIC 전부가 올라타야 하는 공통 바닥이고, 그래서 **Epic 0**로 따로 뺐다.

**배포 경로도 없다.** `cd.yml`은 백엔드 전용이고 관리자 페이지는 S3에 정적 HTML 4개로 올라가 있다. 빌드 결과를 올릴 파이프라인이 없으면 Epic 0의 완료 판정("실데이터 왕복")을 로컬에서만 확인하게 된다. 기획안 §8 개발 순서 1번이 "배포되는 상태를 먼저"인 이유다 → T0.0.

**진척은 화면 수가 아니라 서버 데이터로 동작하는 화면 수로 센다.**

### 권한 체계는 방향이 정해졌고, 계약은 리뷰 중이다

역할 모델은 더 이상 미결이 아니다. 저장소 정본 [`spec/02-role-model.md`](../spec/02-role-model.md) §2와 기획안 §2-3이 일치한다.

- 역할 4종 `MASTER / SUPER / TEAM / HOST` + `teamName` 축
- **Permission 10종** (`ACCOUNT_MANAGE` `CONTENT_MANAGE` `RECRUITMENT_MANAGE` `ATTENDANCE_MANAGE` `ATTENDANCE_APPROVE` `SCORE_MANAGE` `RULE_EDIT` `RULE_ACTIVATE` `EVALUATION` `FINAL_DECISION`)
- **`GET /admin/accounts/me`가 보유 permission 목록을 내려준다**(기획안 §8 공통 처리). 프론트는 사이드바·버튼 노출을 `teamName`이 아니라 **서버가 준 permission 목록**으로 판단한다. 프론트가 매트릭스를 한 벌 더 하드코딩하지 않는다
- 범위 판정(본인 부문/전 부문, 본인 팀/전체)은 **서버 403** — 프론트는 받아서 처리만 한다

백엔드 Admin 도메인이 permission 기반 인가로 재설계 개정판(2026-09-10)을 작성해 **리뷰 중**이다. 그 문서는 permission을 더 세분화(41개)하고 권한 커스텀 화면용 `Permission.values()` 엔드포인트와 "최종 상태" PUT을 포함한다고 전해진다. **다만 그 문서는 이 저장소에 없고 리뷰가 끝나지 않았으므로 확정 사실로 쓰지 않는다.** 10종과 41개의 대응 관계가 문서로 나오기 전까지 T4.4(권한 커스텀 화면)의 규모는 보류다 → 게이트 `G-permission정본`.

**프론트의 권한 게이팅(T4.1)이 기다리는 것은 `/me` 응답에 permission 목록이 실리는 것 하나다.** 이 계약을 백엔드에 요청하는 일은 티켓이 아니라 **지금 할 일**이다.

### 사이드바를 숨기는 것은 보안이 아니다

[`ia/01-ia-strategy.md`](../ia/01-ia-strategy.md) §6이 백엔드 전수 확인으로 발견한 사항이다. 기존 `/api/v1/admin/**`의 인가가 `hasAnyRole("SUPER","TEAM")` 한 줄뿐이었다. 백엔드 permission 설계가 이 1층 URL 게이트를 2층 `@PreAuthorize`로 바꾸는 것을 포함하지만, **그 마이그레이션이 끝나기 전까지 API는 열려 있다.** 프론트의 사이드바 미노출은 UX 의도이지 접근 통제가 아니다. 이 WBS의 권한 게이팅(Epic 4)을 전부 끝내도 마찬가지다 — 실제 차단은 백엔드 2층이 한다.

기획안 §11이 하나 더 짚는다. `SecurityConfig`가 `.anyRequest().permitAll()`이라 **새 `/api/v1/attendance/**`를 명시 등록하지 않으면 출결 입력·조회가 무인증으로 열린다.** 프론트에는 숨은 영향이 있다 — 서버가 인증을 보지 않으면 T0.2의 401 처리 경로가 테스트되지 않은 채 통과한다 → R12.

## 읽는 법

**규모** — 학기 중 학생 운영진 기준. 시험·프로젝트 마감이 끼는 것을 전제한다.

| | 뜻 | 환산 |
| --- | --- | --- |
| `S` | 하루이틀 | 0.3주 |
| `M` | 한 주 | 1주 |
| `L` | 2~3주 | 2.5주 |
| `XL` | 한 달 이상 | 5주 |

**담당** — `F` 프론트, `B` 백엔드, `F+B` 양쪽. EPIC 축은 도메인 단위라 프론트와 백엔드 작업이 한 EPIC에 섞이므로, 티켓마다 표시하지 않으면 병행 그림에서 한쪽 공수가 사라진다(1차 판이 Epic 3을 "백엔드 트랙"으로 묶어 프론트 몫을 지운 것이 그 사례다).

**배지**

| | 뜻 |
| --- | --- |
| `MVP-출결` | 학기 출결을 이 시스템으로 돌리려면 반드시 필요 |
| `MVP-리허설` | 11월 목업 리허설(순서 검증)에 필요 |
| `화면 코드 동결` | 진행 중 다른 사람이 해당 파일을 수정하면 충돌한다 |
| `권한 계약 선행` | `/me` permission 목록 계약이 나와야 착수 |
| `G_` | 앞선 결정이 나야 착수 가능 |

**날짜는 세 개만 관리한다.** 나머지는 순서만 지킨다. 간트는 만들지 않는다 — 가용 시간이 불규칙한 팀에서 날짜 기반 계획은 첫 주에 어긋나고, 유지되지 않는 계획은 없는 것보다 나쁘다. 기간은 **규모 태그 + EPIC별 주수 합산 + 병행 반영**으로 아래 일정 절에서 잰다.

| 기준일 | 날짜 | 관련 |
| --- | --- | --- |
| 리크루팅 리허설 | **11월** | 커트라인 B (목업) |
| **출결 시작일** — 겨울 방학 스터디 1주차 | **2027-01-04 상정** (오늘부터 16.6주) | 커트라인 A. 12월 리크루팅으로 합류한 신입 기수가 방학 스터디부터 새 시스템으로 출결을 시작한다. 편성(명단·HOST 계정)은 이보다 1~2주 앞서 끝나야 하므로 **개발 마감은 12월 중순**으로 본다 |
| 리크루팅 시즌 시작일 | **2026-12-01** (오늘부터 11.7주) | 실전 판정. 11월 말과 같으므로 "시즌 직전으로 연기"는 선택지가 아니다. 이번 시즌은 기존 정적 HTML로 치른다(기획안 §7-2) |
| **프론트 투입 인원** | **2명** | T0.1a 이후 Epic 0을 두 갈래로 병행한다. 백엔드 1명은 T3.1 전담 |

## 완료 판정 — 시나리오 A/B/C

EPIC의 "다 됐다"를 흐름으로 잰다. [`ia/01-ia-strategy.md`](../ia/01-ia-strategy.md) §9의 11월 리허설 워크스루가 시나리오 A의 뿌리다.

### 시나리오 A — 리크루팅 시즌 (Epic 1·2 완료 게이트)

두 단으로 판정한다. **리허설 판정**은 순서 강제가 동작하는지를 목업 상태로 확인하고, **실전 판정**은 같은 흐름이 실데이터로 왕복하는지 확인한다. 리허설 판정 통과는 Epic 2를 닫지 않는다.

| 단계 | 실전 판정 | 리허설 판정 (목업 허용) | 담당 EPIC |
| --- | --- | --- | :-: |
| ① 공고 등록 | 만들고 **새로고침해도 남아 있다.** 기수 중복 시 차단 | — | Epic 1 |
| ② 질문 등록 | 다건 등록·롤백 안내, 순서·라벨 중복 차단 | — | Epic 1 |
| ③ (모집) | 지원자 데이터가 API로 조회되는지만 확인 | — | Epic 2 |
| ④ 평가 | 평가자 계정으로 본인 부문만 보인다. 저장 후 **재로그인해도 유지.** 최종평가 버튼은 대표진에만. 지원자 딥링크 공유 시 상대가 같은 화면을 연다 | — | Epic 2 |
| ⑤ CSV 추출 | 결과 처리 화면 ①단계에서 파일을 받는다. 파일 생성 방식은 `G-CSV방식` 확정에 따른다. **한글 파일명이 깨지지 않는다** | 결과 처리 화면 ①단계에 버튼이 있다 | Epic 2 |
| ⑥ 승격 | ②단계에서 실행. **부분 실패 명단 표시** | ②단계에서 실행되고 상태가 "승격 완료"로 바뀐다 | Epic 2 |
| ⑦ 지원서 삭제 | ③단계에서 실행. ⑤⑥ 미완이면 **비활성 + 사유 표시**. 2단 경고 후 실행 | ⑤⑥ 미완이면 **비활성 + 사유 표시**. 2단 경고 | Epic 2 |

> **⑤⑥⑦ 구간의 메뉴 이동 0회를 회귀 지표로 고정한다.** 현재는 ⑤가 리크루팅 허브, ⑥이 서류 평가 허브에 있어 이동 1회이고 ⑦은 존재하지 않는다. 이 숫자가 1 이상으로 되돌아가면 배치 결정이 되돌려진 것이다. **이 지표는 서버 없이 측정된다** — 목업 리허설이 성립하는 근거다.

### 시나리오 B — 출결 한 주기 (Epic 3 완료 게이트)

기획안 §4-2 흐름. 인증은 **네이버카페 링크**(§4-5 `cafe_link`)이고 증빙 사진은 없다. 점수는 **제출 시 확정**되며 조회 시 재계산하지 않는다(§3-4).

| 구간 | 통과 판정 |
| --- | --- |
| 학기 초 | 편성 없이 시작할 수 없다는 전제가 화면에서 성립한다. 명단 CSV가 **미리보기를 거쳐** 반영되고 `is_leader` 열이 함께 들어온다. `is_scored`를 끄면 그 부원이 점수 화면에서 빠진다 |
| 매주 | **HOST의 랜딩은 "내 스터디"(주차 버튼 목록)이고, 주차를 누르면 입력 화면이 열린다.** 사이드바가 없다. 활동에 설정된 주차 수(`total_weeks`)만큼 버튼이 뜨고 **전 주차가 저장된다**(현재 5주차 이후 미저장 결함 해소). 같은 주차를 두 번 만들 수 없다. 전원 출석이 기본값이다. 카페 링크를 넣고 제출하면 점수가 표시되고, 제출 후 수정이 차단된다. `/admin/**` 진입 시 403 |
| 수시 | 운영진 화면에 **팀별 진행률(예: 8주차 중 3주차)과 미제출 팀 목록**이 표시된다. 제출된 세션의 카페 링크가 열린다. HOST가 올린 인정 요청이 승인함에 쌓이고, 승인 시 **상태와 점수가 함께 바뀌며** 반려 시 사유가 남는다. 운영진 직접 수정은 사유 없이 저장되지 않고, **변경 이력에 이전 상태·점수와 사유가 남는다** |
| 기말 | **새 규칙 버전을 활성화하면 그 이후 확정되는 점수만 새 배점을 따르고, 이미 확정된 점수는 변하지 않는다.** 각 레코드가 적용된 규칙 버전을 함께 보여준다. 인정 승인으로 상태가 바뀌면 그 레코드에 박힌 규칙 버전으로만 재계산된다. 집계는 벌점 누적이며 임계값 초과자가 플래그된다. 화면 표기 코드와 CSV 코드가 일치한다 |

> **기말 판정은 1차 판과 정반대다.** 1차 판은 "규칙 배점을 바꾸면 집계 숫자가 실제로 바뀐다"였는데, 이것은 기획안 §3-4가 금지한 조회 시 재계산을 완료 조건으로 요구한 것이다. §3-4의 이유: "3월 결석 점수가 5월에 규칙이 바뀌었다고 달라지면 소명이 불가능하다. 엑셀을 대체하는 시스템이 엑셀보다 근거가 약하면 안 된다." 현재 코드(`ScoresPage.tsx:40` → `lib.ts:10`)가 고정 배점을 쓰는 것은 맞지만, 고치는 방향은 "규칙을 조회 시 참조"가 아니라 **"서버가 확정한 `point`를 그대로 표시"**다. 그리고 현재 코드는 가점(출석 1 / 지각 0.5 / 결석 0), 기획안 §5-2는 벌점(출석 0 / 지각 0.5 / 결석 1)이라 부호가 반대다.

### 미니 판정 — Epic 5 콘텐츠

시나리오 A/B/C 어디에도 안 걸리므로 자체 판정을 둔다: **FAQ·아카이빙·후기·커리큘럼 각각 등록→새로고침 유지→수정→삭제가 실데이터로 왕복하고, 실패 시 한글 오류가 뜬다.**

> **세 시나리오 어디에도 나오지 않는 항목** — 대시보드 · 설정 · 회원 관리 · 감사 로그 조회. 완료 판정에 쓰이지 않는다 = 핵심 업무 흐름을 막지 않는다. **일정이 압박받으면 여기서 자른다.** 시나리오 위의 항목을 자르면 안 된다.

### 회의는 결정 주체별로 묶는다

1차 판은 게이트를 출결·리크루팅·스택으로 묶었는데 한 묶음 안에 결정 주체가 섞여 있어 그대로는 회의가 성립하지 않는다.

| 순서 | 주체 | 안건 | 형식 |
| --- | --- | --- | --- |
| **1** | **프론트 자체** | G-스택 | 30분. 지금 |
| **2** | **백엔드 확인** | G-permission정본 · G-매트릭스정합 · G-CSV방식 · G-DRAFT지원서 · **`/me` permission 목록 계약 인도 시점** | 사실 확인. 회의 없이 문서 대조로 끝날 수 있다. 지금 요청 |
| **3** | **운영지원팀** | G-출결화면구조 · G-ADV입력 · G-행사출결범위 · BASE 병행 인원 규칙 | 30분. 사진 인증 관련 안건은 전부 삭제 |
| **4** | **대표진** | G-출결상태표기 · G-규칙권한명칭 · G-파괴적작업(승격 취소) · 결과 처리 재확인 | 30분 |

**기술 스택 권장** (G-스택) — 학생 팀에서는 라이브러리를 쓰는 편이 맞다. 기수마다 담당자가 바뀌는데 직접 만든 캐싱·재검증 로직은 만든 사람만 안다. 라우터·서버 상태 관리·폼·스키마 검증은 **도입**, **전역 클라이언트 상태 스토어는 도입하지 않는다.** `App.tsx`가 쥔 상태 대부분(`attendance` `studyTeams` `membersMap` `hosts` `exceptions` `scoreRules`)이 서버가 정본을 갖게 될 서버 상태이고, 남는 클라이언트 상태는 `sidebarOpen` `loginModalOpen` 정도다. 이것을 전역 스토어에 옮기면 `App.tsx`를 스토어 파일로 이름만 바꾸는 결과가 된다. **라우터 도입은 게이트가 아니다** — 어느 역할 모델을 택하든 필요하므로 확정으로 처리한다.

## 크리티컬 패스

**출결 체인이 크리티컬 패스다.** 유일하게 백엔드부터 신규다. 1차 판에서 세 번 등장하던 게이트가 **한 번**(T3.1 앞)으로 줄었다 — 나머지 둘은 기획안이 닫았다.

```
[백엔드]  G-출결상태표기 ─► T3.1 스키마·API 계약·DDL 런북 ───────────────┐
                                                                        │ 계약 확정
[프론트]  T0.0 CD ─► T0.1a 라우터 ─► T0.8 인증 ─► T0.2 ─► T0.3 ─► T0.9 ───┴─► T3.2 편성
                          └► T0.1b 출결 상태 해체 (병행)                        └► T3.3 HOST
                                                                                └► T3.4 HOST 화면
                                                                                   └► T3.5 진행률
                                                                                      └► 커트라인 A
```

**T3.1이 Epic 0 종료 전에 끝나야 한다.** 그러지 않으면 프론트가 Epic 0을 마치고도 출결에 착수하지 못한다. 백엔드 5주 대 프론트 14.8주이므로 순서상 여유는 있지만, DDL 선적용(`ddl-auto: validate`)과 SecurityConfig 등록이 T3.1 안에 있어야 한다.

**준-크리티컬 — 권한 체인.** 이것이 안 끝나면 다른 모든 EPIC의 연동 결과를 검증할 수 없다("누가 봐야 정상인지" 판정 기준이 없다).

```
`/me` permission 목록 계약 ─► T4.1 게이팅 ─┬─► 사이드바 필터
T0.1a 라우터 ──────────────────────────────┴─► 경로 가드 + 403
```
