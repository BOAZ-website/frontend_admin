# 시스템 계정 기능명세서

| 항목 | 내용 |
| --- | --- |
| 범위 | 관리자 콘솔 `시스템·계정` 전체 (계정 및 권한 / 보안) |
| 주 사용자 | 서비스운영팀장(MASTER) |
| 근거 자료 | 시스템 계정 탭 화면 정의서, **Admin 권한 체계 재설계 설계 문서(2026-09-11 개정)** 및 컴팩트판 |
| 상태 | **v1.1** — 권한 재설계 문서 기준으로 4.2 · 3장 · 6장 정리. 화면 레이아웃은 PoC |
| 미결 항목 | 운영팀 정책 확정 1건(`SYS-A-5` 권한 격자, **`SYS-AUTH` 0단계 차단**) · 백엔드 협의 1건(`SYS-A-2` 감사 로그) · 기획·디자인 정리 4건 (6장) |

> **이 문서는 당위 문서이며, 권한 체계의 정본이다.** [`spec/02-role-model.md`](02-role-model.md) §2의 Permission 10종을 **41개 카탈로그로 대체한다.** 역할 4종(`MASTER` · `SUPER` · `TEAM` · `HOST`) 정의는 그대로 유효하며, `TeamName`에 `그룹리더`가 추가된다.
> 현재 화면에 무엇이 구현되어 있는지는 [`screens/05-system.md`](../screens/05-system.md), 개발 순서와 규모는 [`01-wbs.md`](../01-wbs.md)의 Epic 4를 본다.
> 본 문서의 화면 ID(`SYS-*`)와 기능 ID(`ACC-01` 등)는 WBS의 티켓 키·하위 항목과 1:1로 대응한다.

## 1. 문서 목적

- 운영진 계정과 권한 범위를 관리하고, 시스템 내 주요 관리 행위를 확인하는 영역의 **현재 PoC 구성을 정리**한다.
- 백엔드 협의가 선행되어야 확정되는 항목(권한 저장 방식, 감사 로그 범위)을 명확히 분리한다.

> **다른 탭보다 확정도가 낮다.** 화면뿐 아니라 **메뉴 명칭, 탭 구분, 기능의 통합·분리 여부까지 기획 과정에서 변경될 수 있다.**
> 계정 정보, 권한 단위, 변경 가능 항목, 감사 로그 제공 범위는 **실제 API가 제공하는 필드와 동작, 그리고 백엔드 협의 결과**에 맞춰 확정한다.
> 본 문서 4장은 **현재 상태 기록**이며, 구현 지시서가 아니다.

## 3. 공통 사항 — 권한 체계 (권한 재설계 문서 기준)

### 3.1 유효 권한 계산

```
유효 권한 = 기본 세트(role, teamName)     ← 코드 (DefaultPermissions.java)
          − REVOKE + GRANT               ← DB  계정별 오버라이드
          + 리더십 파생                    ← DB  담당 그룹(admin_group_leader)에서 매 요청 계산
```

- **기본 세트는 코드다.** 역할별로 어떤 기능이 되는지의 표(매트릭스)는 `DefaultPermissions.java` 한 파일에 있고, 바꾸려면 배포한다. **화면에서 수정하지 않는다.**
- **계정별 예외는 오버라이드**다. 기본 세트 대비 더한 것(GRANT)·뺀 것(REVOKE)만 저장한다. 이것이 SYS-PERM 화면이 다루는 대상이다.
- **role·teamName이 바뀌면 그 계정의 오버라이드는 전부 삭제**된다. 오버라이드는 절대 목록이 아니라 "그 기본 세트 대비 차이"라서 base가 바뀌면 의미를 잃는다.
- 권한은 JWT에 싣지 않고 매 요청 DB에서 계산한다. 회수가 즉시 반영된다.

### 3.2 기본 세트 키 7개

| 키 (role, teamName) | 매트릭스 열 | 성격 |
| --- | --- | --- |
| `(MASTER, 서비스운영팀)` | 서운팀장 | 계정·권한 관리 포함 전 기능. **평가 4행만 X** (의도) |
| `(SUPER, 대표진)` | 대표진 | 운영 전반. 차기대표진과 `다른 부문 서류 평가` 1행만 다름. **41개 중 실제 포함 범위는 `SYS-A-5`로 미확정** |
| `(SUPER, 차기대표진)` | 차기대표진 | ↑ + 전 부문 평가. **`SYS-A-5`로 미확정** |
| `(TEAM, 서비스운영팀)` | 서비스운영팀 | 계정 조회·감사로그·콘텐츠·리크루팅. 출결 전부 X |
| `(TEAM, 운영지원팀)` | 운영지원팀 | 출결 전반·점수 규칙·HOST 계정 발급 |
| `(TEAM, *)` | 기타 운영진 | **폴백.** 본인 계정 수정 + 본인 부문 서류 평가 + 최종 합불 조회 |
| `(HOST, 그룹리더)` | 스터디장 + ADV팀장 | 본인 계정 수정 하나. 출결 입력 권한은 **리더십 파생**으로 붙음 |

- `Role`은 `MASTER / SUPER / TEAM / HOST` 4종, `TeamName`에 `그룹리더`가 추가된다. `TeamName`은 팀명이 아니라 **운영진의 자리**다.
- 겸임(운영진 × 그룹 리더십)이 가능하다. 유효 권한은 합집합이며, 화면 표시는 리더십 행 기준으로 ADV·스터디를 둘 다 보여준다.
- `HOST` 계정 발급은 **출결 관리 탭 소관**이다. 이 탭은 운영진 계정만 다룬다.
    - 화면 정의서가 가리키던 `SET-HOST`는 출결 v2.0에서 **`ATT-GROUP` 스터디·팀 관리에 흡수**됐다 → [`spec/05-attendance.md`](05-attendance.md) §4.10

### 3.3 Permission 카탈로그 (41개)

| 묶음 | permission |
| --- | --- |
| 계정·시스템 | `ADMIN_ACCOUNT_READ` `ADMIN_ACCOUNT_SELF_WRITE` `ADMIN_ACCOUNT_WRITE` `ADMIN_ACCOUNT_CREATE_DELETE` `ADMIN_PERMISSION_WRITE` `AUDIT_LOG_READ` |
| 콘텐츠 | `CONTENT_READ` `CONTENT_WRITE` |
| 리크루팅 | `RECRUITMENT_NOTICE_READ/WRITE` `APPLICANT_CSV_READ` `APPLICATION_DELETE_ALL` `PRE_NOTIFICATION_READ/DELETE` `MEMBER_PROMOTION_WRITE` |
| 평가·합불 | `EVALUATION_OWN_TRACK_WRITE` `EVALUATION_ALL_TRACK_WRITE` `FINAL_DECISION_READ/WRITE` |
| 출결 관리 | `ATTENDANCE_{BASE,ADV,STUDY,EVENT,SCORE}_{READ,WRITE}` |
| 출결 입력탭 | `ATTENDANCE_{ADV,STUDY}_ENTRY_{READ,WRITE}` · `ATTENDANCE_{ADV,STUDY}_ENTRY_OWN_GROUP_{READ,WRITE}` |
| 기타 | `HOST_ACCOUNT_READ/WRITE` `SCORE_RULE_READ/WRITE` |

- 이름 규칙 `<대상>_<동작>`, 동작은 `READ` / `WRITE` 둘뿐.
- `_OWN_GROUP_` 4개는 기본 세트에 없고 **담당 그룹에서 계산**된다. 계정별 권한 화면에서 체크로 켜고 끌 수 없다.
- PoC 화면의 `ACCOUNT_MANAGE` · `CONTENT_MANAGE` 등 10개 묶음 이름은 **폐기**. 실제 키는 위 41개다.

## 4. 화면별 기능 명세

### 4.1 운영진 계정 관리 `SYS-ACC`

**화면 목적**: 관리자 시스템을 사용하는 운영진 계정과 계정별 역할·권한 상태를 확인하고 관리한다. **서비스운영팀장(MASTER) 전용** 화면이다.

**기능 목록**

| ID | 기능 | 설명 |
| --- | --- | --- |
| ACC-01 | 운영진 계정 조회 | 계정 목록과 기본 정보 확인 |
| ACC-02 | 역할·권한 확인 | 계정에 부여된 역할과 접근 권한 확인 |
| ACC-03 | 계정 발급 | `새 운영진 계정 발급`으로 신규 계정 생성 |
| ACC-04 | 계정 수정 | 계정 정보·역할 변경 |
| ACC-05 | 비밀번호 변경 | 계정별 비밀번호 재설정 |
| ACC-06 | 계정 삭제 | 사용하지 않는 계정 삭제 |

**상단 요약 지표**

전체 활성 운영진 / `MASTER` 인원 / `SUPER` 인원 / `TEAM` 인원

**목록 컬럼**

아이디(`username`) / 성명 / 역할(`role`) / 소속 부서(`team_name`) / 트랙(`track`) / 기수 / 생성 일시 / 관리 액션(비밀번호 변경·수정·삭제)

**필터**: 역할 / 부서 / 트랙 + 아이디·성명 검색

**적용 규칙 (권한 재설계 문서 확정)**

| 규칙 | 내용 |
| --- | --- |
| 계정 권한 3분리 | `ADMIN_ACCOUNT_SELF_WRITE`(본인 정보·비밀번호, 전원) / `ADMIN_ACCOUNT_WRITE`(타인 수정, MASTER) / `ADMIN_ACCOUNT_CREATE_DELETE`(생성·삭제, MASTER) |
| 목록 조회 | `ADMIN_ACCOUNT_READ` 보유자만. 본인 정보는 `/me`로 별도 |
| role·teamName 변경 | 해당 계정의 **오버라이드 전부 삭제** → 변경 전 경고 모달에 명시 |
| 본인 role·teamName 변경 | **금지** (락아웃 방지) |
| 락아웃 방지 | `ADMIN_ACCOUNT_WRITE` 유효 보유자가 1명이면 회수·삭제·비활성화·강등 **네 경로 전부 차단**. 자기 자신의 회수는 카운트와 무관하게 차단 |
| 겸임자 표시 | 소속은 리더십 행 기준으로 ADV·스터디 둘 다 표시 |
| 조합 검증 | `(SUPER, 그룹리더)` 같은 무의미 조합은 권한 0으로 닫힘 → 생성·수정 시 유효 조합 검증 |

> 계정 발급 시 초기 비밀번호를 담당자에게 어떻게 전달하는지 정의가 필요하다. (→ 6장)

### 4.2 계정별 권한 관리 `SYS-PERM`

**화면 목적**: 계정 하나를 골라 **기본 세트 대비 예외(오버라이드)** 를 조정한다. PoC의 "권한 매트릭스"(역할 × 기능 표)는 **화면으로 만들지 않는다** — 기본 세트가 코드라 화면에서 바꿀 수 없고, 권한 재설계 문서가 "요구사항에 없음"으로 버린 대안이다.

**진입**: SYS-ACC 계정 목록 → 계정 선택 → `권한 관리`

**기능 목록**

| ID | 기능 | 설명 |
| --- | --- | --- |
| PERM-01 | 권한 목록 렌더 | `Permission.values()` API로 41개 체크박스 렌더. **프론트 하드코딩 없음.** 3.3절 7묶음으로 그룹핑 |
| PERM-02 | 기본 세트 표시 | 해당 계정 `(role, teamName)` 기본 세트는 기본 체크. 오버라이드로 바뀐 항목만 **강조** — 강조된 것이 곧 커스텀 내역 |
| PERM-03 | 리더십 파생 표시 | `_OWN_GROUP_` 4개는 담당 그룹에서 계산되므로 **읽기 전용**, 체크 불가. 담당 그룹 목록 함께 표시 |
| PERM-04 | 저장 | 체크된 **최종 집합**을 PUT. GRANT/REVOKE 계산은 서버. 저장 시 해당 계정 오버라이드 전삭제 후 재삽입 |
| PERM-05 | 오류 처리 | 자기 자신의 `ADMIN_ACCOUNT_WRITE` 회수 거부 · 마지막 보유자 회수 거부 → 사유 표시 |

**접근**: `ADMIN_PERMISSION_WRITE` 보유자 (기본 세트에서는 `(MASTER, 서비스운영팀)`)

> 프론트가 GRANT/REVOKE를 계산하면 안 된다. 서버가 매번 현재 기본 세트와 diff해야, 나중에 기본 세트가 바뀌어도 저장된 오버라이드가 "의도한 차이"로 남는다.

### 4.3 보안 감사 로그 `SYS-LOG`

**화면 목적**: 관리자 시스템에서 발생한 주요 계정·권한 관련 행위와 변경 이력을 확인한다.

**기능 목록**

| ID | 기능 | 설명 |
| --- | --- | --- |
| LOG-01 | 관리 행위 이력 확인 | 계정·권한 관련 주요 변경 기록 확인 |
| LOG-02 | 이력 추적 | 누가 언제 어떤 관리 작업을 수행했는지 확인 |

**목록 컬럼**

발생 일시 / 수행자(Actor) / 액션 유형 / 대상(Target) / 상세 내용 / IP 주소

**액션 유형 (화면 기준)**

`ACCOUNT_CREATE` (계정 발급) / `PASSWORD_RESET` (비밀번호 재설정) / `PERMISSION_GRANT` (권한 부여)

> **구현한다(확정).** 다만 권한 재설계(v3) 범위 밖이라 **별도 착수** 항목이다 — 감사 로그 구현체가 현재 코드에 없고, 권한 구현이 끝난 뒤 붙인다. 기록 대상은 되돌릴 수 없는 작업(출결 수정 · 콘텐츠 삭제 · 합불 확정 · 승격 · 계정 생성 · 권한 변경 · 지원서 삭제)을 기본안으로 하고, 저장 항목·보관 기간은 착수 시 백엔드와 확정한다. (→ 6장)
> 감사 로그가 없는 동안은 권한 변경 이력이 DB의 오버라이드 행(`granted_by` · `created_at`)으로만 남는다.
> **비가역 작업은 그 공백을 먼저 메운다.** [`04-evaluation.md`](04-evaluation.md) §4.5가 공용 감사 테이블을 정의하고 `PROM-05`·`DEL-05`가 거기에 INSERT한다. `SYS-LOG`는 새 테이블을 만드는 것이 아니라 **그 테이블을 조회 대상으로 삼는다.** 통합도 백필도 필요 없다.

### 4.4 ~~평가자 계정 일괄 생성·회수~~ *(폐기)*

**폐기 사유**: 서류 평가는 **운영진만 수행**하며 외부 평가자를 쓰지 않는다. 권한 설계상 `(TEAM, *)` 폴백에 `EVALUATION_OWN_TRACK_WRITE`가 기본 포함되어, **모든 운영진이 별도 발급 없이 본인 부문 평가 권한을 갖는다.** 전 부문 평가가 필요한 경우는 대표진·차기대표진 기본 세트에 이미 포함된다.

⇒ 평가자용 계정을 따로 만들 필요가 없으므로 이 화면을 두지 않는다. 예외적으로 특정 계정에 평가 권한을 더하거나 뺄 일이 생기면 **4.2절 계정별 권한 관리(SYS-PERM)** 로 처리한다.

---

### 4.5 회원(User) 관리 `SYS-MEM` *(신규 — PoC 화면 없음)*

**화면 목적**: 정회원 승격(서류 평가 EVL-PROM) 결과를 포함해 **현재 회원 명단을 조회**한다. 조회 전용이며, 승격 실행 버튼은 없다.

| ID | 기능 | 설명 |
| --- | --- | --- |
| MEM-01 | 회원 목록 조회 | 기수 · 부문 · 회원 유형(`MEMBER` 등) 필터, 이름 검색 |
| MEM-02 | 승격 결과 확인 | 승격 일시 · 승격 처리자 · 출신 지원서 기수 표시 |
| MEM-03 | 회원 상세 | 기본 정보 · 계정 상태. 출결 개인 타임라인(출결 관리 ATT-TL)으로 연결 |

> **왜 별도 화면이 필요한가.** 승격 화면(`EVL-PROM`)도 명단을 보여주지만, 그 화면의 조회 대상은 지원서다. 리크루팅이 끝나면 [`04-evaluation.md`](04-evaluation.md) §4.4가 지원서를 전부 삭제하므로 `EVL-PROM`은 조회 대상을 잃는다. **승격 이후 시점에 회원을 확인하는 경로가 따로 있어야 한다.**
> 실행과 조회는 시점도 주체도 다르다는 점에서 [`ia/01-ia-strategy.md`](../ia/01-ia-strategy.md) 규칙 2에도 부합한다.
> 원본 화면 정의서에 없어 **본 명세서에서 신규로 정의**한다.
