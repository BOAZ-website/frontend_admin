## 읽는 순서

1. **플랫폼 기반** — 모든 화면이 전제하는 공통 바닥 (라우터 · 인증 · API 클라이언트 · 공용 컴포넌트)
2. **시스템 계정** — 권한 체계(41개 permission · 기본 세트 7키). 다른 명세서의 "권한" 절이 여기를 참조한다
3. 리크루팅 → 서류 평가 → 출결 → 콘텐츠 — 도메인 순서는 자유

## 공통 표기

| 표기 | 뜻 | 예 |
| --- | --- | --- |
| 화면 ID | WBS 티켓 키와 동일 | `ATT-ROSTER` · `REC-POST` |
| 기능 ID | WBS 티켓의 하위 항목 | `ROS-01` · `POST-02` |
| Open Issue | 명세서 접두사 + 분류 + 번호 | `ATT-A-1` · `REC-B-3` · `SYS-C-1` |
| API 확인 | 백엔드에 확인할 항목 | `REC-API-1` · `EVL-API-3` |

**Open Issue 분류**

| 기호 | 뜻 |
| --- | --- |
| `A` | 운영팀 정책 확정 |
| `B` | 디자인 확정 전 정리 |
| `C` | 서비스운영팀 확인 |

화면 ID와 기능 ID는 [`01-wbs.md`](../01-wbs.md)의 티켓 키·하위 항목과 **1:1로 대응한다.** 한쪽을 고치면 다른 쪽도 함께 고쳐야 한다.

## 미결 목록은 어디에 있나

각 명세서의 **Open Issues 절**이 미결 목록이고, 바로 뒤 **잔여 작업(Backlog) 절**이 그에 따라 남은 일이다. 확정된 건은 같은 절 안의 "확정 완료" 또는 "해결 완료" 표로 내린다.

**장 번호는 문서마다 다르다.** 절 이름으로 찾는 편이 안전하다.

| 명세서 | Open Issues | 잔여 작업 |
| --- | --- | --- |
| 리크루팅 · 서류 평가 · 시스템 계정 · 콘텐츠 | 6장 | 7장 |
| 출결 관리 | 9장 | 10장 |
| 플랫폼 기반 | 없음 (기존 WBS 티켓을 옮긴 문서라 자체 미결 항목이 없다) | 없음 |

도메인을 가로지르는 안건은 [`screens/92-open-items.md`](../screens/92-open-items.md)에 있다. 명세서가 답을 준 안건은 그 문서에서 결정 완료로 바뀌고 정본 링크가 붙는다.

## 기준선 문서와의 관계

같은 `spec/` 아래 [`01-attendance-system.md`](01-attendance-system.md)와 [`02-role-model.md`](02-role-model.md)는 **기준선**이라 내용을 고치지 않는다. 기능명세서가 그 위에 얹히는 현재 정본이며, 충돌하면 기능명세서를 따른다.

| 기준선 | 대체된 부분 | 유효한 부분 |
| --- | --- | --- |
| `01-attendance-system.md` | 출결 설계(§3 이후) → [`05-attendance.md`](05-attendance.md) | §2 권한 체계 |
| `02-role-model.md` | Permission 10종(§2) → [`06-system.md`](06-system.md) §3.3의 41개 | §1 역할 4종 정의 |

자세한 문서 체계는 [`docs/README.md`](../README.md)를 본다.
