## 1. 네 갈래로 갈라진 현황

역할 정의가 문서와 코드에 걸쳐 네 곳에 있고, 서로 다르다.

| 출처 | Role 값 | MASTER | HOST | CONTENT_ADMIN |
| --- | --- | :-: | :-: | :-: |
| [`ia/02-ia-tree.md`](../ia/02-ia-tree.md) §2 | `SUPER` `TEAM` | ✕ | ✕ | ✕ |
| **[`01-attendance-system.md`](01-attendance-system.md) §2-2 (정본)** | `MASTER` `SUPER` `TEAM` `HOST` | ● | ● | ✕ |
| `src/entities/user/model/types.ts` (`UserRole`) | `SUPER` `TEAM` `HOST` `CONTENT_ADMIN` | ✕ | ● | ● |
| `src/pages/system-accounts/…` (`AdminRole`) | `MASTER` `SUPER` `TEAM` | ● | ✕ | ✕ |

### 정본의 정의

| Role | 주체 | 성격 |
| --- | --- | --- |
| `MASTER` | 서비스운영팀장 | 계정 발급·시스템 관리 + 아카이빙·모집 CUD |
| `SUPER` | 대표진 3명 + 차기대표진 | **의사결정만.** 규칙 확정 · 최종 합불 · 출결 인정 |
| `TEAM` | 그 외 운영진 | 소속 팀 실무 + 서류 평가 |
| `HOST` | 스터디장 · ADV 팀장 | **출결 입력만.** Permission 없음 |

### `CONTENT_ADMIN`은 어디서 왔나

정본에 없는 값이다. 코드에서 이 역할은 사이드바 푸터에서 **"서비스운영팀"**으로 표기되고, 로그인 시 아카이빙 화면으로 진입한다. 즉 정본의 `TEAM`(서비스운영팀원)에 해당하는 자리를 새 이름으로 만든 것으로 보인다.

문제는 그러면서 정작 `MASTER`가 전역 역할 체계에서 빠졌다는 점이다. 결과적으로 **시스템·계정 화면은 `MASTER` 기준으로, 나머지 화면은 `CONTENT_ADMIN` 기준으로 판정**하게 되어 있다.

## 2. Permission 10종 (정본)

[`01-attendance-system.md`](01-attendance-system.md) §2-3에 정의된 열거값이다.

| # | Permission | 설명 |
| --- | --- | --- |
| 1 | `ACCOUNT_MANAGE` | 운영진 계정 생성·삭제·권한 부여 |
| 2 | `CONTENT_MANAGE` | 아카이빙·FAQ·후기·커리큘럼 |
| 3 | `RECRUITMENT_MANAGE` | 공고·질문·CSV |
| 4 | `ATTENDANCE_MANAGE` | 활동·팀·명단·세션·HOST 계정 |
| 5 | `ATTENDANCE_APPROVE` | 출결 수동 수정·인정 |
| 6 | `SCORE_MANAGE` | 활동 점수 입력 |
| 7 | `RULE_EDIT` | 점수 규칙 DRAFT 작성·수정 |
| 8 | `RULE_ACTIVATE` | 점수 규칙 활성화(확정) |
| 9 | `EVALUATION` | 서류 평가 |
| 10 | `FINAL_DECISION` | 최종 합불 |

> **구현 화면의 매트릭스가 9행인 것은 라벨 오류가 아니다.** `RULE_EDIT`와 `RULE_ACTIVATE`를 `RULE_EDIT / ACTIVATE` 한 행으로 합친 결과이며, 메뉴 라벨 "10대 Permission"은 정확하다.
>
> 다만 정본이 둘을 나눈 것은 **규칙 초안을 쓰는 사람과 확정하는 사람을 분리할 수 있게** 하려는 의도로 읽힌다. 점수 규칙은 전 부원의 수료 판정에 직결되므로, 병합 유지 여부는 아래 §3.3에서 결정한다.

권한 매트릭스(기능 × 역할)는 [`01-attendance-system.md`](01-attendance-system.md) §2-5가 정본이다. **이 문서에 옮겨 적지 않는다** — 표를 두 곳에 두면 반드시 어긋난다. 화면 문서([`screens/05-system.md`](../screens/05-system.md))도 마찬가지로 참조만 한다.

## 3. 결정이 필요한 사항

역할 정의가 하나로 정해지기 전에는 **접근 제어를 구현할 수 없다.** 아래 셋이 선행 조건이다.

### 3.1 `CONTENT_ADMIN`을 어떻게 할 것인가

| | |
| --- | --- |
| **현재** | 전역 `UserRole`에만 존재하고 정본에는 없다. 사이드바 푸터는 이 값을 "서비스운영팀"으로 표기한다. |
| **결정할 것** | ⓐ `TEAM` + `teamName=서비스운영팀`으로 흡수할지, ⓑ 정본에 정식 역할로 추가할지 |
| **결정 주체** | 서비스운영팀 + 백엔드 |
| **바뀌는 것** | 로그인 후 랜딩 규칙, 사이드바 노출 규칙, 계정 생성 화면의 역할 선택지 |

정본이 Role(무엇을 할 수 있나)과 TeamName(어느 실무를 맡나) 두 축으로 나눈 구조를 유지한다면 ⓐ가 일관된다.

### 3.2 `UserRole`과 `AdminRole` 타입 일원화

| | |
| --- | --- |
| **현재** | 전역 상태는 `MASTER`를 모르고, 시스템·계정 화면은 `HOST`를 모른다. |
| **결정할 것** | 정본 4종으로 통일할지, 두 타입의 용도를 명시적으로 분리할지 |
| **결정 주체** | 백엔드 + 프론트 |
| **바뀌는 것** | 계정 관리 화면의 역할 선택지, 전 화면의 권한 판정 기준 |

### 3.3 `RULE_EDIT` / `RULE_ACTIVATE` 화면 분리 여부

| | |
| --- | --- |
| **현재** | 점수 규칙 화면에서 DRAFT 작성과 활성화를 같은 사람이 연달아 할 수 있다. |
| **결정할 것** | 작성자와 확정자를 분리할지(정본의 의도), 지금처럼 병합할지 |
| **결정 주체** | 대표진 |
| **바뀌는 것** | 점수 규칙 화면의 버튼 노출 조건, 권한 매트릭스 표의 행 수 |

## 4. 권한 제어 적용 시 함께 처리할 것

역할 정의가 정해진 뒤 접근 제어를 붙일 때 반드시 같이 다뤄야 하는 항목이다.

- **정본의 접근 제어는 2중 구조다.** [`ia/02-ia-tree.md`](../ia/02-ia-tree.md) §0은 "비활성화가 아니라 미노출"을, §4는 "미노출 경로 직접 진입 시 403 (랜딩으로 리다이렉트 X)"을 요구한다. 현재는 라우터가 없어 **두 번째 층을 만들 수 없다.** → [`screens/91-ia-gap.md`](../screens/91-ia-gap.md) §5
- **HOST는 경로로도 막는다.** [`01-attendance-system.md`](01-attendance-system.md) §2-4는 HOST가 `/api/v1/admin/**`에 접근할 수 없고 `/api/v1/attendance/**`만 허용된다고 정의한다.
- **최종 평가 버튼은 `SUPER` 전용이다.** [`ia/02-ia-tree.md`](../ia/02-ia-tree.md) 3.2에 `※ role=SUPER 에만 노출`로 명시되어 있으나 현재 전 계정에 노출된다.
- **PoC용 역할 전환 장치를 제거한다.** 시스템·계정 화면의 "로그인 시뮬레이션"과 헤더의 "계정 전환"은 클라이언트에서 역할을 바꾸는 통로다. 실제 인증을 붙이면서 남겨두면 권한 우회 경로가 된다.
