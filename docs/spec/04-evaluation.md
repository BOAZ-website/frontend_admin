# 서류 평가 기능명세서

| 항목 | 내용 |
| --- | --- |
| 범위 | 관리자 콘솔 `서류 평가` 전체 (서류 심사 / 합격 및 승격) |
| 주 사용자 | 평가자(서류 심사), 운영진(최종 결과 관리) |
| 근거 자료 | 서류 평가 탭 화면 정의서, 기존 백엔드 API 명세 |
| 상태 | **PoC 단계** — 화면은 디자인 확정본이 아님 |
| 미결 항목 | 디자인 확정 전 정리 6건 (6장) — 운영 정책 미결 없음 |

> **이 문서는 당위 문서다.** 현재 화면에 무엇이 구현되어 있는지는 [`screens/03-evaluation.md`](../screens/03-evaluation.md), 개발 순서와 규모는 [`01-wbs.md`](../01-wbs.md)의 Epic 2를 본다.
> 본 문서의 화면 ID(`EVL-*`)와 기능 ID(`DASH-01` 등)는 WBS의 티켓 키·하위 항목과 1:1로 대응한다.

## 1. 문서 목적

- 제출된 지원서 평가부터 전체 지원자 제출 상태 확인, **최종 합불 및 정회원 승격까지의 흐름**을 기능 단위로 정리한다.
- 평가자와 운영진의 역할이 갈리는 지점, 그리고 되돌릴 수 없는 처리(정회원 승격)의 확인 절차를 식별한다.

> **구현 기준**: 화면에 노출하는 지원자 정보, 제출 상태, 평가 값과 처리 가능한 액션은 **현재 백엔드 API가 제공하는 필드와 동작 범위**에 맞춰 구성한다.
>
> **전제**: 현재 화면은 UI/UX 디자인 작업 전 **PoC 수준의 구조안**이다. 최종 디자인 단계에서 노출 필드·상태 처리·평가 및 최종 합불 동작을 재정리하고, 평가자와 운영진의 작업 동선을 검토한 뒤 확정한다. 본 문서 4장은 **현재 상태 기록**이며 화면 레이아웃 자체는 확정 명세가 아니다.

## 2. 기능 구조 (IA)

| 그룹 | 화면 | 화면 ID | 대상 |
| --- | --- | --- | --- |
| 서류 심사 | 서류 평가 대시보드 (SUBMITTED) | EVL-DASH | 제출 완료 지원자 |
| 서류 심사 | 전체 지원자 현황 (DRAFT 포함) | EVL-ALL | 임시저장 포함 전체 지원자 |
| 합격 및 승격 | 최종 합불 및 정회원 승격 | EVL-PROM | 최종 합격자 |
| 합격 및 승격 | 지원서 전체 삭제 | EVL-DEL | 종료된 모집의 지원서 (신규 · PoC 없음) |

세 화면은 상단 탭으로 연결되며, 동일 기수를 기준으로 동작한다.

**운영 흐름**

```
지원서 접수(Epic 1) → 제출 완료(SUBMITTED) 대상 서류 평가
   → 평가자별 평가 입력 → 최종 판정(합격 / 보류 / 불합격)
   → 최종 합격자 정회원(MEMBER) 승격 → 지원서 전체 삭제 → 리크루팅 종료
```

## 3. 공통 사항

### 3.1 지원자 제출 상태

| 상태 | 의미 | 평가 대상 |
| --- | --- | --- |
| `DRAFT` | 임시저장 — 작성 중이며 제출하지 않음 | 제외 |
| `SUBMITTED` | 제출 완료 | **평가 대상** |

- 서류 평가 대시보드(EVL-DASH)는 `SUBMITTED`만, 전체 지원자 현황(EVL-ALL)은 `DRAFT`를 포함한 전체를 다룬다.

### 3.2 최종 판정 값

| 판정 | 키 | 의미 |
| --- | --- | --- |
| 합격 | `PASS` | 최종 선발 |
| 보류 | `HOLD` | 판단 유보 |
| 불합격 | `FAIL` | 기준 미달 |
| 미판정 | `PENDING` | 심사 진행 중 |

### 3.3 공통 필터

전 화면 공통으로 **트랙 필터**, **최종 판정 필터**, **지원자명·대학교·전공 검색**을 제공한다.

## 4. 화면별 기능 명세

### 4.1 서류 평가 대시보드 `EVL-DASH`

**화면 목적**: 지원서를 제출 완료한 지원자를 대상으로 서류 평가를 진행하고 평가 현황을 확인한다.

**기능 목록**

| ID | 기능 | 설명 |
| --- | --- | --- |
| DASH-01 | 제출 완료 지원자 조회 | 실제 서류 평가 대상 목록 확인 |
| DASH-02 | 지원서 확인 및 평가 | `평가하기`로 지원자별 제출 내용을 확인하고 평가 진행 |
| DASH-03 | 평가 진행 현황 확인 | 지원자별 평가 진행 여부와 결과 확인 |
| DASH-04 | 최종 판정 입력 | 지원자별 합격 / 보류 / 불합격 선택. **평가자 집계는 참고값이고 최종 결정은 대표진·차기대표진(`FINAL_DECISION_WRITE` 보유자)이 직접 지정** |
| DASH-05 | 평가 이력 보존 | 개인 평가 수정 시 덮어쓰기 대신 이력으로 보존 |

**상단 요약 지표**

| 지표 | 내용 |
| --- | --- |
| 제출 지원서 | `SUBMITTED` 상태 건수 |
| 내 심사 완료 | 로그인한 평가자의 진행률 (예: 2/5, 40%) |
| 최종 합격(PASS) | 합격 처리 인원 |
| 최종 보류(HOLD) | 보류 처리 인원 |
| 최종 불합격(FAIL) | 불합격 처리 인원 |
| 판정 미결(PENDING) | 심사 진행 중 인원 |

**목록 컬럼**

지원자 성명(NAME) / 부문(TRACK) / 대학교·본전공 / 졸업 예정 / 합격(PASS) / 보류(HOLD) / 불합격(FAIL) / 총점(SCORE) / 내 평가(MY) / 최종 평가 / 서류 심사(`평가하기`)

- 합격·보류·불합격 컬럼은 **평가자별 판정 집계 수**를 표시한다. 여러 평가자가 같은 지원자를 평가하는 구조다.
- `내 평가`는 로그인한 평가자 본인의 판정, `최종 평가`는 확정 판정을 의미한다.

**최종 판정 확정 규칙 (확정)**

- 평가자들은 각자 의견을 내고, 목록의 합격·보류·불합격 컬럼은 그 **집계(참고값)** 다.
- **최종 판정은 대표진·차기대표진이 직접 지정**한다. 다수결 자동 확정이 아니다.
- 따라서 `최종 평가` 컬럼은 `FINAL_DECISION_WRITE` 보유자에게만 활성화된다. 일반 평가자에게는 조회만 노출한다.

**보류(HOLD) 처리 (확정)**

- 보류는 평가 과정의 **임시 상태**이며, 모든 지원자는 최종적으로 합격 또는 불합격으로 닫힌다.
- 따라서 **최종 확정 시점에 `HOLD`와 `PENDING`이 0건**이어야 한다. 남아 있으면 확정 액션을 차단하고 잔여 건수·명단을 표시한다.

### 4.2 전체 지원자 현황 `EVL-ALL`

**화면 목적**: 제출 완료 여부와 관계없이 리크루팅에 지원한 **전체 지원자의 상태를 한 번에 확인**한다.

| ID | 기능 | 설명 |
| --- | --- | --- |
| ALL-01 | 전체 지원자 조회 | 제출 완료 지원자뿐 아니라 임시저장(`DRAFT`) 지원자까지 포함 |
| ALL-02 | 지원 상태 확인 | 지원자별 현재 제출 상태 구분 표시 (`DRAFT` 배지) |
| ALL-03 | 지원자 현황 관리 | 전체 지원 규모와 제출 진행 상태를 운영 관점에서 확인 |

- 목록 구조는 서류 평가 대시보드와 동일하되, `DRAFT` 지원자는 총점이 0이고 판정 값이 비어 있다.
- 접수 기간 중 **제출 전환율 파악**과 미제출자 관리에 사용한다.

> `DRAFT` 지원자의 지원서 내용을 평가자가 열람할 수 있는지는 확인이 필요하다. (→ 6장)

### 4.3 최종 합불 및 정회원 승격 `EVL-PROM`

**화면 목적**: 서류 평가 이후 최종 합격/불합격 결과를 관리하고, 최종 합격자를 **정회원으로 승격 처리**한다.

**기능 목록**

| ID | 기능 | 설명 |
| --- | --- | --- |
| PROM-01 | 최종 합불 결과 확인 | 지원자별 최종 선발 결과 확인 |
| PROM-02 | 승격 대상 선택 | 체크박스로 대상 선택, `승격 대상 전체 선택` 지원 |
| PROM-03 | 정회원 승격 실행 | 선택한 인원을 BOAZ 정회원(`MEMBER`)으로 일괄 전환. **취소 기능 없음** — 실행 전 확인 모달로 방지 |
| PROM-04 | 승격 현황 확인 | 합격자 수 / 승격 대기 / 승격 완료 인원 확인 |

**상단 요약 지표**

최종 합격자(PASS) / 승격 대기 / 정회원 승격 완료(MEMBER)

**목록 컬럼**

선택 / User ID / 지원자 성명 / 합격 부문 / 이메일 주소(계정 ID) / 연락처 / 대학교·본전공 / 계정 상태 및 권한(`APPLICANT`) / 승격 상태(`승격 대기`)

**승격 처리 동작**

- 선택한 지원자의 계정 권한이 **지원자(`APPLICANT`) → 정회원(`MEMBER`)** 으로 전환된다.
- 선택 인원을 서버에 일괄 전달해 처리하는 방식이며, 개별 처리가 아닌 **일괄 실행**이다.
- 화면에는 평가 점수를 노출하지 않고 **최종 명단만** 표시한다.

**승격 취소 (확정)**

- **화면에 승격 취소 기능을 두지 않는다.** 승격은 기수당 1회뿐이고, 확인 모달로 오조작을 막는 편이 비용 대비 효율적이다.
- 실행 전 확인 모달에 **대상 인원 수와 명단**을 명시하고, "되돌릴 수 없습니다"를 문구로 노출한다.
- 오승격이 실제로 발생하면 백엔드에서 직접 처리한다. 실행 기록은 감사 로그(SYS-LOG) 대상이다.

### 4.4 지원서 전체 삭제 `EVL-DEL` *(신규 — PoC 화면 없음)*

**화면 목적**: 리크루팅이 종료된 뒤 해당 모집의 **지원서 데이터를 일괄 삭제**한다. 불합격자 개인정보를 보관하지 않기 위한 처리로, 정회원 승격이 끝난 뒤에만 실행한다.

**기능 목록**

| ID | 기능 | 설명 |
| --- | --- | --- |
| DEL-01 | 삭제 가능 조건 확인 | 모집 공고 비활성 + 최종 합격자 승격 완료 두 조건을 화면에 표시. 미충족 시 실행 버튼 비활성 + 사유 표시. CSV 추출 완료 여부도 함께 표시 |
| DEL-02 | 삭제 대상 요약 | 대상 기수 · 지원서 건수 · 승격 완료 인원 표시 |
| DEL-03 | 전체 삭제 실행 | 2단 확인(경고 → 기수 입력) 후 해당 모집의 지원서 전체 삭제 |
| DEL-04 | 결과 표시 | 삭제 건수 · 실패 건 표시 |

**삭제 시점 (확정)**

- **리크루팅이 종료되면 삭제**한다. 별도 보관 기간을 두지 않는다.
- 삭제 전 지원자 데이터가 필요하면 **CSV 추출(REC-CSV)을 먼저 완료**해야 한다. 삭제 후에는 복구할 수 없으므로 확인 모달에 CSV 추출 완료 여부를 함께 표시한다.

**제약**

- 모집 진행 중(접수 기간 내 또는 공고 활성 상태)에는 서버에서 차단한다.
- 승격 대기 인원이 남아 있으면 실행할 수 없다. 승격 데이터가 먼저 `User`로 이관되어야 한다.
- 되돌릴 수 없는 처리다. 실행 기록은 감사 로그(시스템·계정 SYS-LOG)에 남긴다.

> 이 화면은 원본 화면 정의서에 없어 **본 명세서에서 신규로 정의**한다. 승격(EVL-PROM) 다음 단계로 배치하고, 순서를 강제할지(승격 미완료 시 진입 자체 차단)는 디자인 단계에서 결정한다.

## 5. API 요구사항

영역별 API가 구현되어 있어 **신규 API 요구는 없다.** 디자인 확정 시 다음을 확인한다.

| ID | 확인 항목 | 사유 |
| --- | --- | --- |
| EVL-API-1 | 총점(SCORE) 산출 규칙 | 평가자별 점수의 합인지 평균인지, 평가 항목 구성은 무엇인지 확인 |
| EVL-API-2 | 최종 판정 확정 규칙 | 평가자 다수 판정에서 최종 값을 결정하는 방식이 API에 있는지, 운영진이 직접 지정하는지 확인 |
| EVL-API-3 | 승격 API 재실행 동작 | 이미 승격된 대상이 포함됐을 때의 처리(중복 무시 / 오류)와 실패 건 반환 형식 확인 |
| EVL-API-4 | DRAFT 지원자 조회 범위 | 임시저장 지원서의 본문을 관리자 API가 반환하는지 확인 |
| EVL-API-5 | 평가자 권한 구분 | 평가자와 운영진의 접근 범위가 권한 모델에서 어떻게 구분되는지 확인 |
| EVL-API-6 | 지원서 전체 삭제 API | 모집 단위 일괄 삭제 엔드포인트 존재 여부, 모집 진행 중 차단 로직 위치 |
