| 항목 | 내용 |
| --- | --- |
| 범위 | 관리자 콘솔 `리크루팅 공고` 전체 (공고 및 문항 / 지원자 데이터) |
| 운영 주체 | 서비스운영팀 |
| 근거 자료 | 리크루트 공고 탭 화면 정의서, 기존 백엔드 API 명세 |
| 상태 | **PoC 단계** — 화면은 디자인 확정본이 아님 |
| 미결 항목 | 서비스운영팀 결정 1건(미리보기 존치), 디자인 확정 전 정리 5건 (6장) |

## 1. 문서 목적

- 모집 공고 등록부터 지원서 문항 설정, 지원자 데이터 확인 및 추출까지 **리크루팅 운영 전 과정의 기능을 정리**한다.
- 디자인 단계에서 다시 정리해야 할 항목과, 운영팀이 결정해야 할 항목을 식별한다.

> **구현 기준**: 화면에 노출하는 데이터와 등록·수정 동작은 **현재 백엔드에 구현된 API가 제공하는 필드와 기능을 우선 기준**으로 구성한다.
>
> **전제**: 현재 화면은 UI/UX 디자인 작업 전 **PoC 수준의 구조안**이다. 최종 디자인 단계에서 노출 필드·동작·상태 처리를 재정리하고, 서비스운영팀의 리크루팅 업무 동선을 검토한 뒤 확정한다. 본 문서 4장은 **현재 상태 기록**이며 화면 레이아웃 자체는 확정 명세가 아니다.

## 2. 기능 구조 (IA)

| 그룹 | 화면 | 화면 ID | 용도 |
| --- | --- | --- | --- |
| 공고 및 문항 | 모집 공고 관리 | REC-POST | 공고 등록·운영 |
| 공고 및 문항 | 지원서 문항 설정 | REC-QST | 지원서 문항 구성 |
| 공고 및 문항 | 지원자 화면 미리보기 | REC-PRV | 지원자 관점 확인 (필요 여부 검토 중) |
| 지원자 데이터 | 지원서 CSV 추출 | REC-CSV | 접수 데이터 추출 |
| 지원자 데이터 | 사전 알림 명단 | REC-ALM | 신청자 조회·삭제, 안내 문구 생성 |

**운영 흐름**

```
사전 알림 명단 수집 → 모집 공고 등록 → 지원서 문항 설정 → (미리보기 확인)
   → 접수 진행 → 지원서 CSV 추출 → 서류 평가(Epic 2)로 연결
```

## 3. 공통 사항

- 관련 API는 **모집 공고 / 지원서 문항 / 지원자 / 사전 알림** 영역별로 이미 구현되어 있다. 관리자 화면은 기존 API 연동 작업에 해당한다.
- 트랙 구분은 전 화면 공통으로 **데이터 분석 / 데이터 엔지니어링 / 데이터 시각화** 3종을 사용하며, 문항 설정에서는 여기에 **전체 공통(COMMON)** 이 추가된다.

## 4. 화면별 기능 명세

### 4.1 모집 공고 관리 `REC-POST`

**화면 목적**: 새로운 리크루팅 모집 공고를 등록하고, 공고 운영에 필요한 정보를 관리한다.

**기능 목록**

| ID | 기능 | 설명 |
| --- | --- | --- |
| POST-01 | 공고 목록 조회 | 기수별 공고를 카드 형태로 조회. 기수 배지, 상태(모집 마감 / 모집 예정), 등록일 표시 |
| POST-02 | 공고 등록 | `새 모집 공고 등록` 모달로 신규 공고 생성 |
| POST-03 | 공고 수정 | 등록된 공고의 기본 정보 수정 |
| POST-04 | 공고 삭제 | 공고 삭제 |
| POST-05 | 홍보 책자 확인 | 등록된 홍보 브로슈어(PDF) 확인 |
| POST-06 | 전형 일정 관리 | 공고별 전형 단계와 일정 구간 관리 |

**공고 등록 입력 필드**

| 필드 | 키 | 필수 | 비고 |
| --- | --- | --- | --- |
| 모집 기수 | `term` | 필수 | 예: 29 |
| 접수 시작일 | — | 필수 | 날짜 선택 |
| 접수 마감일 | — | 필수 | 날짜 선택 |
| 홍보 책자 PDF URL | — | 선택 | S3 URL 입력 |
| 공고 활성화 | — | — | 체크박스. 기본값 활성 |

**공고 카드 표시 정보**

| 영역 | 내용 |
| --- | --- |
| 헤더 | 기수 배지, 상태 배지, 등록일, 공고 제목 |
| 접수 기간 | 시작·마감 일시 (초 단위까지 표기) |
| 현황 지표 | 모집 기수 / 작성된 지원서 건수 / 제출 완료 건수 / 홍보 브로슈어 등록 여부 |
| 전형별 상세 일정 | 서류 접수 → 1차 서류 발표 → 2차 면접 진행 → 최종 합격자 발표, 각 구간 일정 |
| 액션 | 홍보 책자(PDF) 보기 / 수정 / 삭제 |

### 4.2 지원서 문항 설정 `REC-QST`

**화면 목적**: 리크루팅 지원서에서 지원자에게 받을 문항을 설정한다.

**기능 목록**

| ID | 기능 | 설명 |
| --- | --- | --- |
| QST-01 | 문항 목록 조회 | 트랙 탭별 등록 문항 확인. 탭에 문항 수 표시 |
| QST-02 | 문항 추가 | `새 문항 추가` 모달로 문항 생성 |
| QST-03 | 문항 수정 | 등록된 문항 내용·설정 수정 |
| QST-04 | 문항 삭제 | 문항 삭제 |
| QST-05 | 순서 변경 | 문항 카드의 위·아래 이동 |
| QST-06 | 표 형식 문항 | `multiple: true` 문항의 행 헤더 · 열 항목 정의 UI |

**트랙 탭 구성**

`전체 공통` / `컨퍼 공통 문항` / `데이터 분석 트랙` / `데이터 엔지니어링 트랙` / `데이터 시각화 트랙`

**문항 입력 필드**

| 필드 | 키 | 필수 | 비고 |
| --- | --- | --- | --- |
| 트랙 구분 | — | 필수 | 전체 공통(COMMON) / 트랙별 |
| 문항 라벨 (표기명) | — | 필수 | 예: `공통3` |
| 문항 내용 (질문 텍스트) | — | 필수 | 지원자에게 보이는 질문 |
| 문항 보조 설명 | — | 선택 | 답변 작성 시 참고 가이드 |
| 문항 유형 | — | 필수 | 예: 장문 서술형(`LONG_TEXT`) |
| 글자수 제한 | `limitLength` | — | 예: 800 |
| 필수 응답 여부 | `isRequired` | — | 체크박스 |

**표 형식 문항**

일부 문항은 `multiple: true` 메타데이터로 **표 구조 입력**을 지원한다. 행 헤더(예: 과목/라이브러리명, 수준도, 활용 경험 및 프로젝트)와 열 항목을 각각 정의한다.

### 4.3 지원자 화면 미리보기 `REC-PRV`

**화면 목적**: 설정한 모집 공고와 지원서 문항이 지원자 관점에서 어떻게 보이는지 확인하는 **참고 화면**이다.

| ID | 기능 | 설명 |
| --- | --- | --- |
| PRV-01 | 트랙별 미리보기 | 분석 / 엔지니어링 / 시각화 트랙 뷰 전환 |
| PRV-02 | 실시간 렌더링 | 실제 지원서와 동일한 형태로 공고 정보, 기본 인적 사항, 문항, 글자수 카운터 표시 |

> **이 화면은 존치 여부가 미확정이다.** 실제 필요 여부는 서비스운영팀 내부 논의 후 결정하며, 운영상 불필요하다고 판단되면 제거할 수 있다. (→ 6장)

### 4.4 지원서 CSV 추출 `REC-CSV`

**화면 목적**: 모집 기간 동안 접수된 지원자 데이터를 운영 및 평가에 활용할 수 있도록 CSV로 추출한다.

| ID | 기능 | 설명 |
| --- | --- | --- |
| CSV-01 | 트랙별 추출 | 분석 / 엔지니어링 / 시각화 트랙 카드에서 각각 CSV 즉시 다운로드 |
| CSV-02 | 대상 현황 표시 | 카드별 대상 기수와 지원자 수 표시 |

- 추출 항목과 형식은 **현재 구현된 지원자 관련 API가 제공하는 데이터 기준**으로 구성한다.
- 추출 결과는 **평가 종료 후 결과 처리(승격 · 삭제)의 선행 자료**이며, 지원서 전체 삭제(`EVL-DEL`) 전 백업 수단이다. 평가 자체는 API 기반이라 CSV를 입력으로 쓰지 않는다 → [`04-evaluation.md`](04-evaluation.md) §4.4

### 4.5 사전 알림 명단 `REC-ALM`

**화면 목적**: 리크루팅 시작 전 웹사이트 신청 폼으로 수집된 **사전 알림 신청자 명단을 확인**하고, 안내 문구를 만들어 복사한다. 실제 발송은 담당자가 카카오톡 등 외부 메신저로 직접 한다.

> **신청자 = 아직 지원자가 아닌 외부 예비 지원자.** 웹사이트 `POST /api/v1/recruitment/subscriptions`(공개 API)로 이름·연락처·관심 분야를 남긴 사람이다. 명단은 이 경로로만 들어온다.

**기능 목록**

| ID | 기능 | 설명 |
| --- | --- | --- |
| ALM-01 | 신청자 명단 조회 | 검색 + 관심 분야 필터, 결과 건수 표시. `PRE_NOTIFICATION_READ` |
| ALM-02 | 신청자 삭제 | 개별 삭제 · 전체 삭제. `PRE_NOTIFICATION_DELETE`, PLT-CONFIRM 확인 모달 |
| ALM-03 | 메시지 양식 편집 | 기본 양식 설정 · 복원 · 복사, 치환 변수 `{name} {term} {track} {start_date} {end_date}`. 양식은 **서버 저장** (현재 localStorage → 이전) |
| ALM-04 | 실시간 미리보기 | 카카오톡 / 문자 화면 형태로 최종 문구 확인 |
| ALM-05 | 메시지 복사 | 개별 · 전체 명단용 복사. 필터 적용 시 전체 선택 범위는 필터 결과로 한정 |

**명단 테이블 컬럼**

신청자 / 관심 분야(TYPE) / 연락처·이메일 / 신청 일시(DATE) / 액션(삭제)

**PoC 대비 제거되는 기능** (권한 모델 기준 — 사전 알림은 `READ` · `DELETE` 두 permission만 존재)

| 제거 항목 | 사유 |
| --- | --- |
| 신청자 직접 등록 | 등록 permission 없음. 명단은 공개 신청 폼으로만 수집 |
| 발송 상태 토글 · `발송 상태` 컬럼 | 상태를 기록할 WRITE permission 없음. 발송은 시스템 밖에서 일어나 시스템이 알 수 없음 |
| 맞춤 알림 발송 열 | 위와 동일 |

> 발송 이력이 필요하면 담당자가 외부(카톡 단톡방 등)에서 관리한다. 시스템 내 발송 상태는 두지 않는다.

| ID | 확인 항목 | 사유 |
